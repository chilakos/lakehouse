    Create five Terraform modules following the Research architecture patterns. Update the root main.tf to properly wire modules together.

    1. `modules/nessie/` -- Nessie catalog deployment via Helm:
       - `main.tf`: Use `helm_release` resource to deploy Nessie from Bitnami chart. Configure:
         - versionStoreType = JDBC_POSTGRESQL
         - PostgreSQL enabled with configurable password (sensitive variable)
         - replicaCount from variable (default 2)
         - Catalog configuration: default warehouse, S3/MinIO endpoints, regions
         - TLS: Configure HTTPS on Nessie API endpoint (Quarkus TLS config) using cert-manager generated certs (reference a secret name)
         - Use `templatefile()` for values.yaml.tpl to inject environment-specific settings
       - `variables.tf`: environment, namespace, nessie_replicas, nessie_db_password (sensitive), s3_bucket, s3_region, minio_endpoint, minio_bucket, minio_access_key (sensitive), minio_secret_key (sensitive), tls_secret_name
       - `outputs.tf`: nessie_endpoint (including http/https prefix), nessie_internal_endpoint
       - `values.yaml.tpl`: Helm values template with all Nessie configuration (per Research Pattern 1)

    2. `modules/trino/` -- Trino cluster deployment via Helm:
       - `main.tf`: Use `helm_release` for Trino chart. Configure:
         - Coordinator with HTTPS enabled (http-server.https.enabled=true, port 8443)
         - Worker count from variable (default 2)
         - Iceberg catalog properties via REST catalog type pointing to Nessie (per Research: connector.name=iceberg, iceberg.catalog.type=rest, iceberg.rest-catalog.uri pointing to nessie_endpoint)
         - LDAP authentication configuration (password-authenticator.properties) -- values templated from variables
         - File-based access control (access-control.properties pointing to rules.json) -- rules file content from variable
         - TLS keystore configuration for HTTPS
         - JVM config with memory settings based on instance size
       - `variables.tf`: environment, namespace, trino_workers, coordinator_memory, worker_memory, nessie_endpoint, ldap_url, ldap_user_bind_pattern, ldap_user_base_dn, tls_keystore_path, tls_keystore_password (sensitive), access_control_rules (JSON string)
       - `outputs.tf`: trino_endpoint, trino_coordinator_service
       - `values.yaml.tpl`: Helm values with catalog config, security config, resource limits

    3. `modules/s3/` -- AWS S3 bucket configuration with encryption:
       - `main.tf`:
         - `aws_kms_key` resource for S3 encryption (description, enable_key_rotation=true, deletion_window_in_days=30)
         - `aws_kms_alias` for the key
         - `aws_s3_bucket` for lakehouse data (bucket name from variable with environment prefix)
         - `aws_s3_bucket_server_side_encryption_configuration` with SSE-KMS using the KMS key (sse_algorithm = "aws:kms")
         - `aws_s3_bucket_versioning` enabled
         - `aws_s3_bucket_public_access_block` (block all public access)
         - `aws_s3_bucket_lifecycle_configuration` for incomplete multipart upload cleanup
         - IAM policy document for Nessie and Trino service accounts to access the bucket
       - `variables.tf`: environment, bucket_name_prefix, kms_key_deletion_window, tags
       - `outputs.tf`: bucket_name, bucket_arn, kms_key_arn, kms_key_id, iam_policy_arn

    4. `modules/minio/` -- MinIO configuration (not deployment -- team operates MinIO):
       - `main.tf`: This module does NOT deploy MinIO (team already operates it). Instead it:
         - Creates a `null_resource` with provisioner that runs mc commands to create buckets (lakehouse-data, lakehouse-onprem) and set encryption policies
         - Stores MinIO endpoint and credentials as outputs (from variables)
         - Creates a Kubernetes secret with MinIO credentials for Nessie/Trino to consume
       - `variables.tf`: minio_endpoint, minio_access_key (sensitive), minio_secret_key (sensitive), bucket_names (list), namespace
       - `outputs.tf`: minio_endpoint, bucket_names, credentials_secret_name

    5. `modules/networking/` -- VPC and security groups (stub for Phase 1):
       - `main.tf`: Create security groups allowing:
         - Nessie API (19120) from Trino and ETL workloads
         - Trino coordinator (8443) from authorized CIDR blocks
         - PostgreSQL (5432) from Nessie only
         - MinIO (9000) from Nessie and Trino
         - All services: TLS (443) outbound for S3 access
       - `variables.tf`: vpc_id, allowed_cidrs, environment, tags
       - `outputs.tf`: nessie_sg_id, trino_sg_id, postgres_sg_id

    6. Update `infra/terraform/main.tf` -- Wire all modules together:
       - Remove .gitkeep references, add proper module blocks
       - Pass outputs from one module as inputs to another (s3 bucket -> nessie, nessie endpoint -> trino)
       - Use terraform workspace for environment isolation

    IMPORTANT per locked decisions:
    - Separate Trino cluster and Nessie catalog per environment (full isolation)
    - Use REST catalog type for Trino-Nessie connection (not Nessie-specific type)
    - PostgreSQL as Nessie metadata backing store
    - TLS on all endpoints for SEC-06
    - SSE-KMS for S3 for SEC-05

    Create five GitHub Actions workflows implementing the locked decision: branch-based environment promotion (feature branches -> PR to dev -> merge to staging -> merge to main/prod).

    1. `ci/.github/workflows/ci.yml` -- PR validation (update existing stub from Plan 01):
       Trigger: pull_request to dev, staging, main branches
       Jobs:
       - **python-lint**: Setup Python 3.11, install ruff, run `ruff check etl/` and `ruff format --check etl/`
       - **python-test**: Setup Python 3.11, install dependencies from etl/pyproject.toml, run `cd etl && pytest tests/unit/ -x --tb=short`
       - **terraform-validate**: Setup Terraform (hashicorp/setup-terraform@v3), run `cd infra/terraform && terraform init -backend=false && terraform validate`
       - **terraform-fmt**: Run `terraform fmt -check -recursive infra/terraform/`
       All jobs run in parallel. Use `actions/checkout@v4`.

    2. `ci/.github/workflows/deploy-dev.yml` -- Deploy to dev on merge to dev branch:
       Trigger: push to dev branch
       Jobs:
       - **deploy**:
         - permissions: id-token: write, contents: read (OIDC for AWS)
         - Setup AWS credentials via OIDC (aws-actions/configure-aws-credentials@v4, role-to-assume from secrets)
         - Setup Terraform
         - `cd infra/terraform && terraform init && terraform workspace select dev && terraform plan -var-file=environments/dev/terraform.tfvars -out=tfplan`
         - `terraform apply tfplan`
         - Run integration tests against dev environment (optional, gated by test success)

    3. `ci/.github/workflows/deploy-staging.yml` -- Deploy to staging on merge to staging branch:
       Trigger: push to staging branch
       Same structure as deploy-dev but:
       - workspace select staging
       - var-file=environments/staging/terraform.tfvars
       - Requires manual approval via GitHub environment protection rules (add `environment: staging` to job)

    4. `ci/.github/workflows/deploy-prod.yml` -- Deploy to prod on merge to main:
       Trigger: push to main branch
       Same structure as deploy-staging but:
       - workspace select prod
       - var-file=environments/prod/terraform.tfvars
       - `environment: production` with required reviewers
       - Additional step: run smoke tests after deploy (health check on Nessie and Trino endpoints)

    5. `ci/.github/workflows/infra.yml` -- Terraform plan on infra changes (PR only):
       Trigger: pull_request paths: ['infra/**']
       Jobs:
       - **plan**:
         - Setup AWS credentials via OIDC
         - terraform init, terraform plan for each environment (dev, staging, prod)
         - Post plan output as PR comment using `actions/github-script@v7`
         - Do NOT run terraform apply (plan only for review)

    IMPORTANT:
    - Use OIDC for AWS authentication (no long-lived credentials) -- per Research state-of-the-art
    - Reference secrets via ${{ secrets.AWS_ROLE_ARN }} (do not hardcode ARNs)
    - All workflows must have proper `permissions` blocks (least privilege)
    - Use `actions/checkout@v4` and `hashicorp/setup-terraform@v3` (pinned major versions)

    Also create symlink for GitHub workflow discovery:

    - Actually, GitHub requires workflows in `.github/workflows/` at repo root. Create a note in ci/README.md explaining that workflows are authored in ci/.github/workflows/ and symlinked to .github/workflows/. Create the symlink.
