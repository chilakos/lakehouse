Walkthrough of the semantic model YAML lifecycle from GitHub to Snowflake and Fabric

THE PROBLEM
Why do we need a semantic layer?
Your Gold Iceberg tables have column names like LEDGER_BAL_AMT, DISCOUNT_RT, and PRODUCT_LINE_CD. When a business user asks "what was net revenue by product line?" — the LLM has to figure out that:
"net revenue" = SUM(LEDGER_BAL_AMT * (1 - DISCOUNT_RT))
"product line" = PRODUCT_LINE_CD from the DIM_PRODUCT table, joined via ACCOUNT_TYPE_CD = PRODUCT_ID
Without a semantic layer, the LLM guesses from raw column names and gets it wrong. The semantic layer is a translation map between business language and physical schema. It tells the LLM exactly which columns to use, how to aggregate them, and how to join tables.
Think of it as a data dictionary that the AI can read — but structured as code, not a PDF on SharePoint.
THE YAML FILE
What's inside the semantic model
The YAML file in your GitHub repo defines four things:
1. Metrics
Business calculations. "Net revenue" = SUM(LEDGER_BAL_AMT * (1 - DISCOUNT_RT)). Defined once, used everywhere.
2. Dimensions
Things you group by. "Product line", "branch", "customer segment". Maps business names to physical column names.
3. Relationships
How tables join. fact_account_balance.ACCOUNT_TYPE_CD → dim_product.PRODUCT_ID. Tells the LLM which JOINs are valid.
4. Verified queries
Example question-SQL pairs. "What is total balance by product line?" → exact correct SQL. These are few-shot examples that dramatically improve accuracy.
Here's what a metric looks like in the YAML:
metrics: - name: total_net_revenue description: > Net revenue after discounts, summed across accounts expr: SUM(LEDGER_BAL_AMT * (1 - DISCOUNT_RT)) data_type: NUMBER default_aggregation: sum
WHERE IT LIVES
GitHub is the source of truth
The YAML file lives in your lakehouse repo alongside the ADRs and pipeline code. It's version controlled, PR-reviewed, and deployed via CI/CD — just like everything else.
github.com/chilakos/lakehouse/ ├── docs/ │ ├── adr/ │ │ ├── 010-fabric-import-semantic-layer.md │ │ └── 011-snowflake-cortex-semantic-layer.md │ └── architecture/ │ ├── semantic-model-template.yaml ← this file │ └── fastapi-trust-boundary-spec.yaml ├── decks/ └── src/ └── pipelines/
When someone wants to add a new metric or change a dimension, they:
1. Edit the YAML in a feature branch
2. Open a PR — team reviews the business logic
3. Merge to main
4. CI/CD deploys to Snowflake (and later Fabric)
The semantic model gets the same rigor as your ETL code. No one edits metrics in a UI and forgets to tell the team.
PHASE 1 DEPLOYMENT
YAML → Snowflake semantic view
Your CI/CD pipeline reads the YAML and translates it into Snowflake CREATE SEMANTIC VIEW DDL. Here's what happens to the "net revenue" metric:
In the YAML (what you author):
- name: total_net_revenue expr: SUM(LEDGER_BAL_AMT * (1 - DISCOUNT_RT))
CI/CD translates to
In Snowflake (what gets deployed):
CREATE OR REPLACE SEMANTIC VIEW RBC_LAKEHOUSE.GOLD.ENTERPRISE_SEMANTIC_VIEW TABLES ( fact_bal AS GOLD.FACT_ACCOUNT_BALANCE_DAILY, dim_prod AS GOLD.DIM_PRODUCT ) COLUMNS ( fact_bal.LEDGER_BAL_AMT AS "Ledger balance" METRIC, fact_bal.DISCOUNT_RT AS "Discount rate" FACT, dim_prod.PRODUCT_LINE_CD AS "Product line" DIMENSION ) METRICS ( "Net revenue" AS SUM(fact_bal.LEDGER_BAL_AMT * (1 - fact_bal.DISCOUNT_RT)) ) RELATIONSHIPS ( fact_bal(ACCOUNT_TYPE_CD) REFERENCES dim_prod(PRODUCT_ID) );
The semantic view is a metadata object — it doesn't copy or transform any data. It just tells Cortex Analyst: "when someone says 'net revenue', here's the formula. When they say 'product line', here's the column and join."
AT QUERY TIME
How Cortex Analyst reads the semantic view
When a user asks "What was net revenue by product line for Q4?", Cortex Analyst doesn't guess. It reads the semantic view and knows exactly what to do:
User: "net revenue by product line for Q4"
↓ Cortex Analyst reads semantic view
Resolves: "net revenue" → SUM(LEDGER_BAL_AMT * (1 - DISCOUNT_RT))
Resolves: "product line" → dim_product.PRODUCT_LINE_CD
Resolves: join path → fact.ACCOUNT_TYPE_CD = dim.PRODUCT_ID
Resolves: "Q4" → BALANCE_DT BETWEEN '2025-10-01' AND '2025-12-31'
↓ generates SQL
Executes SQL against Iceberg external tables
Without the semantic view, Cortex Analyst would see raw column names like LEDGER_BAL_AMT and DISCOUNT_RT and have to guess whether "net revenue" means SUM(LEDGER_BAL_AMT) or SUM(LEDGER_BAL_AMT - DISCOUNT_RT) or something else entirely. The semantic view removes the guessing.
The verified queries in the YAML (step 1) also help here — they're few-shot examples that Cortex Analyst uses to pattern-match similar questions it hasn't seen before.
PHASE 2 DEPLOYMENT
Same YAML → Fabric semantic model
When Fabric comes online, the same YAML deploys to a second target. The CI/CD pipeline translates the same metric definitions into a Power BI tabular model (TMDL format):
Snowflake (Phase 1)
YAML → CREATE SEMANTIC VIEW
Cortex Analyst reads it
SQL runs on Snowflake warehouse
Data: Iceberg external tables
Fabric (Phase 2)
YAML → TMDL / Power BI model
Fabric Data Agent reads it
DAX runs on VertiPaq engine
Data: Delta copy in OneLake
Here's what happens to the same "net revenue" metric in Fabric:
In the YAML (same file, unchanged):
- name: total_net_revenue expr: SUM(LEDGER_BAL_AMT * (1 - DISCOUNT_RT))
CI/CD translates to
In Fabric (TMDL / DAX measure):
measure 'Total Net Revenue' = SUMX( fact_account_balance, fact_account_balance[LEDGER_BAL_AMT] * (1 - fact_account_balance[DISCOUNT_RT]) ) relationship fact_account_balance[ACCOUNT_TYPE_CD] → dim_product[PRODUCT_ID] many-to-one
Same metric, same business definition, two engines. When a Power BI user sees "Total Net Revenue" in a report, it's the exact same formula as when RBC Assist answers "what was net revenue?" via Cortex Analyst.
THE CI/CD PIPELINE
How deployment actually works
When someone merges a YAML change to main, GitHub Actions runs:
# .github/workflows/deploy-semantic-model.yml on: push: branches: [main] paths: - 'docs/architecture/semantic-model-template.yaml' jobs: deploy-snowflake: steps: - name: Validate YAML schema run: python scripts/validate_semantic_model.py - name: Generate Snowflake DDL run: python scripts/yaml_to_snowflake_ddl.py --input semantic-model-template.yaml --output semantic_view.sql - name: Deploy to Snowflake run: snowsql -f semantic_view.sql --account $SF_ACCOUNT --authenticator oauth --token $SF_DEPLOY_TOKEN deploy-fabric: # Phase 2 — uncomment when ready # steps: # - name: Generate TMDL # run: python scripts/yaml_to_tmdl.py # - name: Deploy to Fabric # run: tabular-editor deploy ...
The yaml_to_snowflake_ddl.py script is a straightforward Python translator — it reads your YAML metrics/dimensions/relationships and generates CREATE SEMANTIC VIEW SQL. You'd build this once. The Fabric equivalent (yaml_to_tmdl.py) generates Power BI tabular model definitions — you build it when Phase 2 starts.
What you build for Phase 1:
1. The YAML file (already in the repo as the template)
2. A YAML → Snowflake DDL translator (Python script, ~200 lines)
3. A GitHub Actions workflow to deploy on merge

What you add for Phase 2:
4. A YAML → TMDL translator (Python script)
5. A second deployment step in the same workflow

The semantic model YAML is the linchpin. It's the single artifact that ensures "net revenue" means the same thing whether you're asking RBC Assist (Cortex Analyst), building a Power BI report (Fabric Import model), or querying Trino directly (the YAML documents the formula for humans too).
