Step-by-step walkthrough of how RBC Assist queries data through FastAPI and Snowflake Cortex

OVERVIEW
The request lifecycle
A user asks RBC Assist a question. Here's every hop that question takes, what API gets called at each stage, and what comes back. Tap through to follow a real query end to end.
1. RBC Assist → FastAPI trust boundary
2. FastAPI authenticates + classifies
3. FastAPI → Snowflake Cortex Agent API
4. Cortex Agent → Cortex Analyst (NL-to-SQL)
5. Cortex Analyst → Semantic view → Iceberg
6. Results flow back through the chain
Example query we'll trace: "What was total net revenue by product line for Q4 2025?"
STEP 1 — RBC ASSIST → FASTAPI
The user asks a question
RBC Assist sends the NL question to your FastAPI trust boundary. This is the only API the consumer app ever calls. It never talks to Snowflake or Fabric directly.
POST/v1/query
{ "question": "What was total net revenue by product line for Q4 2025?", "conversation_id": null, "options": { "max_rows": 100, "include_sql": true, "include_explanation": true } } Headers: Authorization: Bearer <user-entra-id-token> X-Trace-Id: "trace-7f3a2b1c" X-Backend-Hint: "auto"
Key detail: The Bearer token is the user's Entra ID access token — not a service account. This is what enables per-user security enforcement downstream.
STEP 2 — INSIDE FASTAPI
Authenticate, classify, route
FastAPI does three things before calling any backend:
2a. Validate + exchange token
Validates the Entra ID token. Exchanges it for an OBO (on-behalf-of) token scoped to Snowflake. The OBO token carries the user's identity so Snowflake RBAC applies to this specific user.
2b. Guardrails
Scans the question for prompt injection patterns, PII, and restricted data references. If anything triggers, FastAPI returns a 422 with a guardrail violation — the query never reaches Snowflake.
2c. Classify + route
The orchestrator LLM classifies the query intent. "Total net revenue by product line" is a structured analytics question → routes to Snowflake Cortex. If it were a BI report request, it would route to Fabric (Phase 2). If it were about a policy document, it would route to Cortex Search.
The X-Backend-Hint header is optional. If the caller sends snowflake, FastAPI skips classification and routes directly. auto means "you decide."
STEP 3 — FASTAPI → CORTEX AGENT
Calling the Snowflake Cortex Agent API
FastAPI calls the Snowflake Cortex Agent REST API. The agent orchestrates across structured (Analyst) and unstructured (Search) tools. You can skip the Agent and call Cortex Analyst directly for pure NL-to-SQL — but the Agent gives you both in one call.
POST/api/v2/cortex/agent/run
{ "agent": "RBC_LAKEHOUSE.GOLD.RBC_ASSIST_AGENT", "thread": { "messages": [{ "role": "user", "content": "What was total net revenue by product line for Q4 2025?" }]}, "stream": true } Headers: Authorization: Snowflake Token="<obo-session-token>" Content-Type: application/json
The agent was pre-created in Snowflake with this config:
{ "name": "RBC_ASSIST_AGENT", "models": { "orchestration": "claude-4-sonnet" }, "tools": [{ "tool_spec": { "type": "cortex_analyst_text_to_sql", "name": "enterprise_analyst" } }, { "tool_spec": { "type": "cortex_analyst_sql_exec", "name": "sql_executor" } }], "instructions": { "orchestration": "For any revenue, balance, or transaction question, use enterprise_analyst. For policy questions, use search." } }
The orchestration model is Claude 4 Sonnet running inside Snowflake Cortex. No data leaves Snowflake's boundary.
STEP 4 — CORTEX AGENT → CORTEX ANALYST
NL-to-SQL via the semantic view
The Cortex Agent decides this is a structured data question and invokes Cortex Analyst. Analyst reads your semantic view to understand the business meaning of "net revenue" and "product line," then generates SQL.
What Cortex Analyst sees
Your semantic view (ENTERPRISE_SEMANTIC_VIEW) tells it:
metric: total_net_revenue expr: SUM(LEDGER_BAL_AMT * (1 - DISCOUNT_RT)) dimension: product_line expr: PRODUCT_LINE_CD table: dim_product time_dimension: balance_date expr: BALANCE_DT relationship: fact → dim_product on: ACCOUNT_TYPE_CD = PRODUCT_ID
What Cortex Analyst generates
SELECT p.PRODUCT_LINE_CD AS product_line, SUM(b.LEDGER_BAL_AMT * (1 - b.DISCOUNT_RT)) AS total_net_revenue FROM GOLD.FACT_ACCOUNT_BALANCE_DAILY b LEFT JOIN GOLD.DIM_PRODUCT p ON b.ACCOUNT_TYPE_CD = p.PRODUCT_ID WHERE b.BALANCE_DT BETWEEN '2025-10-01' AND '2025-12-31' GROUP BY p.PRODUCT_LINE_CD ORDER BY total_net_revenue DESC;
This SQL runs on a Snowflake virtual warehouse under the user's role. Row access policies and RBAC apply — the user only sees data they're authorized for.
This is the key: the semantic view maps business language ("net revenue") to physical columns (LEDGER_BAL_AMT * (1 - DISCOUNT_RT)). Without it, the LLM would have to guess column names from raw schema — and get it wrong.
STEP 5 — EXECUTION
SQL hits Iceberg via external tables
The generated SQL executes against Snowflake external tables that point to your Gold Iceberg V2 files. Here's the data path:
SQL executes on Snowflake warehouse
↓ reads
External tables (Iceberg table format)
↓ points to
External volume (S3/MinIO on-prem)
↓ reads
Gold Iceberg V2 Parquet files (Nessie catalog)
Zero-copy
No data is copied into Snowflake. The external volume is a pointer to your on-prem object storage. Snowflake's query engine reads the Parquet files directly, using Iceberg metadata from the Nessie catalog to find the right files and apply partition pruning.
Security enforcement
Snowflake RBAC applies at query time. If the user's role doesn't have access to a particular product line's data, those rows are filtered out — the LLM never sees them, and neither does the user.
STEP 6 — RESPONSE
Results flow back
The results reverse the path: Snowflake → Cortex Agent → FastAPI → RBC Assist. Here's what FastAPI returns to the consumer:
200 OK
{ "query_id": "q_7f3a2b1c", "conversation_id": "conv_new_abc123", "backend": "snowflake", "answer": "Total net revenue by product line for Q4 2025: Lending: $142.3M Deposits: $98.7M Cards: $67.1M Investments: $54.2M Insurance: $31.8M", "data": { "columns": [ {"name": "product_line", "type": "string"}, {"name": "total_net_revenue", "type": "number"} ], "rows": [ ["Lending", 142300000], ["Deposits", 98700000], ["Cards", 67100000], ["Investments", 54200000], ["Insurance", 31800000] ], "row_count": 5, "truncated": false }, "sql": "SELECT p.PRODUCT_LINE_CD ...", "metadata": { "semantic_model": "ENTERPRISE_SEMANTIC_VIEW", "execution_time_ms": 1240, "backend_request_id": "sf-01J7..." } }
RBC Assist gets back: the NL answer (for display), the raw data (for charts/tables), the generated SQL (for transparency), and metadata (for audit). The conversation_id enables follow-up questions like "Break that down by region" — FastAPI passes it back to Cortex Agent which maintains the thread context.
STEP 7 — FEEDBACK LOOP
User feedback improves accuracy
When a user thumbs-up or thumbs-down a result, RBC Assist calls the feedback endpoint:
POST/v1/query/feedback
{ "query_id": "q_7f3a2b1c", "rating": "positive", "correction": null }
What happens with feedback
Positive ratings confirm the SQL was correct. FastAPI logs the question + SQL pair and can push it to Cortex Analyst as a verified query — a few-shot example that improves future accuracy for similar questions.
Negative ratings with corrections ("it should have excluded intercompany transfers") feed into the semantic model refinement cycle — the team updates the YAML, PR reviews it, CI/CD redeploys the semantic view.
Full API surface summary:

POST /v1/query — ask a question, get a routed answer
POST /v1/query/stream — same, with SSE streaming
POST /v1/query/feedback — thumbs up/down + corrections
GET /v1/health — backend connectivity check
GET /v1/backends — list available backends + semantic models
