AI Semantic Layer SWOT Analysis

Build NL-to-SQL vs Buy Commercial Solution

Decided | Decision: Build-own with Claude on Bedrock | 2026-03-14 | Prepared for: Leadership Review

Executive Summary
The AI semantic layer strategy was evaluated between building a custom NL-to-SQL engine using Claude on AWS Bedrock versus purchasing a commercial NL-to-SQL solution (ThoughtSpot, Databricks AI/BI, Snowflake Cortex). The build-own approach was selected based on its unique integration with the existing Cube semantic layer, full control over prompt engineering for financial services domain accuracy, and AWS Bedrock's data residency guarantees.

The NLToSQLEngine in etl/src/semantic/nl_to_sql.py integrates with Cube YAML definitions via metric_context.py, using actual measure and dimension names as LLM prompt context. This approach produces more accurate SQL than generic commercial solutions because the prompt includes the exact metric definitions and domain-specific few-shot examples.

Recommendation
Build-own with Claude on Bedrock is recommended and already operational. The NLToSQLEngine integrates with Cube metric definitions for context-aware SQL generation, golden datasets provide accuracy benchmarking per domain, and AWS Bedrock ensures data stays within the VPC.

Key advantages over commercial alternatives: ThoughtSpot and Databricks AI/BI require their own data platform (vendor lock-in), Snowflake Cortex ties AI features to Snowflake (conflicts with compute-only Snowflake strategy), and all commercial solutions have limited customization of prompt engineering for domain-specific accuracy.

Scaling decision (2026-03-30): ADR-006 adopts Retrieval-Augmented Schema Linking (RASL) with pgvector to scale from 2 to 200+ Cube-modeled tables. ADR-009 extends the AI layer with an AI Data Hub for RAG-based entity retrieval (client briefs, risk narratives, surveillance context) alongside NL-to-SQL. Accuracy thresholds (90%/70%) apply to Cube-modeled Gold tables only — unmodeled tables are out of scope for NL-to-SQL.

AI chatbot integration (2026-04-01 — ADR-010): RBC Assist (the enterprise AI chatbot) is now grounded in Gold-layer data via Fabric Data Agent → NL2DAX → Azure AI Foundry. The Fabric Import semantic model (ADR-010) serves as the data grounding layer: Fabric Data Agent generates DAX queries against the semantic model, executes them with the end user's Entra ID identity, and returns governed structured answers. Raw data never leaves RBC's environment. This path complements the existing NL-to-SQL (Cube → Claude on Bedrock) path: Fabric Data Agent handles analyst-facing BI questions via DAX; the RASL NL-to-SQL engine (ADR-006) handles schema-linked SQL generation for Gold table exploration.

SWOT Overview

Strengths

  • S1: Cube YAML Integration for Context-Aware SQL Generation — The NLToSQLEngine uses metric_context.py to load Cube YAML definitions as LLM prompt context. SQL generation uses actual measure names (total_notional, total_var_95), dimension names (symbol, side, account_id, sector), and table references (gold.trading_metrics, gold.risk_exposure) rather than generic schema discovery.
  • S2: Claude on Bedrock Provides Enterprise-Grade LLM — AWS Bedrock deployment ensures all data stays within the VPC -- no external API calls, no data leaving the network boundary. Claude Sonnet provides strong SQL generation capabilities with the ability to follow domain-specific instructions.
  • S3: Golden Dataset Evaluation Framework — The golden_datasets directory contains per-domain test cases for accuracy benchmarking. Each dataset has natural language questions paired with expected SQL output, enabling automated accuracy measurement and regression detection.
  • S4: Full Control Over Prompt Engineering — Building in-house provides complete control over prompt structure, few-shot examples, chain-of-thought reasoning, and domain-specific instructions. Financial services terminology and calculation rules can be embedded directly in the prompt.
  • S5: Model-Agnostic Architecture — The NLToSQLEngine architecture is model-agnostic -- the prompt format works with any LLM that supports text-to-SQL generation. Claude on Bedrock is the current choice, but switching to a different model (Anthropic API, open-source model) requires only a configuration change.

Weaknesses

  • W1: Ongoing Prompt Maintenance as Schema Evolves — When Cube metric definitions change (new measures, renamed dimensions, new cubes), the NL-to-SQL prompts must be updated to reflect the new schema. This creates an ongoing maintenance burden tied to schema evolution.
  • W2: LLM Accuracy Variability for Complex Joins — LLM-generated SQL for complex multi-table joins, nested subqueries, and window functions is less reliable than simple aggregation queries. Accuracy drops for queries that require reasoning about table relationships.
  • W3: No Commercial Support Contract — A build-own solution has no vendor support contract. Bug fixes, feature development, and accuracy improvements rely entirely on internal engineering capacity.

Opportunities

  • O1: Domain-Specific Fine-Tuning Possible — The build-own approach enables domain-specific prompt optimization that commercial solutions cannot match. Financial services terminology, calculation conventions, and regulatory reporting patterns can be embedded directly in the prompt template.
  • O2: Few-Shot Examples Per Domain Improve Accuracy Over Time — As users ask questions and validate results, correct question-SQL pairs can be added to the golden dataset and few-shot example library. Accuracy improves continuously without code changes or model retraining.
  • O3: Claude Model Upgrades Improve Quality Without Code Changes — When Anthropic releases improved Claude models on Bedrock, the NLToSQLEngine benefits from accuracy improvements by updating the model_id configuration. No prompt rewriting or architecture changes needed.
  • O4: Reusable Evaluation Framework for AI Quality — The golden dataset evaluation framework built for NL-to-SQL can be reused for other AI capabilities (data quality suggestions, anomaly detection, automated documentation). The investment in evaluation infrastructure has broad applicability.

Threats

  • T1: Bedrock Pricing Changes — AWS Bedrock pricing for Claude model invocations may change as the service matures. Increased usage (more users, more complex queries) amplifies cost exposure.
  • T2: LLM Hallucination Risk for Financial Queries — LLMs can generate syntactically valid SQL that produces incorrect results for financial calculations. In a financial services context, incorrect query results could lead to wrong trading decisions or regulatory reporting errors.
  • T3: Model Deprecation and API Changes — LLM models are regularly updated and deprecated. Claude model versions on Bedrock may be retired, requiring migration to newer versions with potential accuracy changes.
  • T4: Competitive Commercial Solutions Improving Rapidly — ThoughtSpot, Databricks AI/BI, and Snowflake Cortex are investing heavily in NL-to-SQL accuracy. Commercial solutions may eventually match or exceed custom solution accuracy with less maintenance effort.
