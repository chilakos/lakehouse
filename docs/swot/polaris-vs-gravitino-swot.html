Fundamental Philosophy Difference
🏔️ Polaris — The Specialist
Polaris does one thing: Iceberg REST catalog. Stores table pointers, manages snapshots, enforces RBAC, vends credentials, handles atomic commits. Zero ambiguity. Narrowness is a feature. Every line of code serves the Iceberg use case. Think of it as a precision scalpel.
🌎 Gravitino — The Generalist
Gravitino is a unified metadata control plane for your entire data and AI estate. Federates Iceberg, Hive, MySQL, Kafka, HDFS, Delta, Paimon, ML models, and vector stores under one namespace. Has a Table Maintenance Service, MCP server for AI agents, audit logging, lineage. Think of it as a Swiss Army knife.
The core question for RBC: Laser-focused Iceberg catalog that does one thing perfectly (Polaris), or federation layer that unifies legacy and modern metadata during a multi-year migration (Gravitino)? Removing Teradata OTF from the architecture has largely answered this in Polaris's favour.

Apache Polaris — Full SWOT
S
Strengths
  • Most complete Iceberg REST spec — reference-quality implementation, designed alongside spec authors at Snowflake + Iceberg community
  • Best credential vending — S3 (AssumeRole), ADLS (SAS), GCS (OAuth2), MinIO STS. Scoped, short-lived tokens per table. Battle-tested via Snowflake production
  • ASF TLP (Feb 2026) — graduated, vendor-neutral governance. Not Snowflake’s project anymore
  • Diverse, high-quality PMC — Snowflake, Dremio, Google, Microsoft, Confluent, LanceDB, Bloomberg, Starburst across 13 members
  • Snowflake Open Catalog — managed Polaris with zero config for Snowflake cloud burst. Polaris IS Snowflake’s catalog
  • Dremio Open Catalog — commercial enterprise offering with SLA, table maintenance, lineage, governance on top of OSS Polaris
  • Quarkus runtime — lightweight, fast startup, native compilation support, low memory overhead
  • OPA integration (v1.3) — externalize authorization to Open Policy Agent; policy-as-code via Rego
  • Realm-based multi-tenancy — hard isolation for business unit separation
  • 2,800+ PRs, 100+ contributors — fastest contributor growth of any Iceberg catalog in 2024–2025
  • Clean, focused codebase — narrow scope means fewer bugs, easier to audit, lower operational complexity
  • Iceberg V3 aligned — Dremio/Snowflake are dominant V3 contributors; Polaris will be first-mover on new spec features
  • Bloomberg on PMC — implies financial services production use at scale
W
Weaknesses
  • Iceberg-only — cannot federate HMS, Hive, MySQL, Kafka, or non-Iceberg metadata. Requires Gravitino for legacy migration federation
  • PostgreSQL-only backend — no MySQL, MongoDB, H2. Limits deployment flexibility in some enterprise environments
  • No row/column-level security — RBAC is table/namespace level. Iceberg REST FGAC spec is in active PR but not ratified. Privacera fills this gap
  • No branching / WAP workflows — no Git-for-data versioning natively. Write-Audit-Publish requires Nessie or external mechanism
  • No native AD/LDAP integration — requires external OIDC bridge (Keycloak) for Active Directory. Extra infrastructure component vs Gravitino’s native Kerberos
  • No UI / governance portal — purely API-driven. No built-in data catalog browser or lineage viewer
  • No built-in table maintenance — compaction, snapshot expiry, cleanup only in Dremio commercial offering
  • Snowflake/Dremio concentration — despite TLP, ~80% of core commits from these two vendors. Community diversity improving but not balanced
  • Limited self-hosted bank-scale evidence — production evidence is Snowflake managed, not self-hosted enterprise deployments
  • No multi-format support — Delta Lake, Hudi, Paimon cannot be managed by Polaris
O
Opportunities
  • Iceberg REST FGAC spec — when ratified, Polaris implements catalog-native row/column security, reducing engine-side enforcement dependency
  • Polaris federation (v1.3) — ability to sync and proxy external catalogs (Nessie, Gravitino, Lakekeeper) creates unified namespace without migration
  • Nessie merge roadmap — Dremio announced Nessie capabilities (branching, WAP) would flow into Polaris natively
  • Iceberg V3 first-mover — Polaris will be first to implement V3 catalog features (VARIANT, deletion vectors, row-level lineage)
  • Financial services traction — Bloomberg and Starburst on PMC signal regulated industry adoption growing
  • Growing managed service options — both Snowflake and Dremio offer enterprise SLA managed Polaris, reducing operational risk
T
Threats
  • Vendor concentration risk — Snowflake and Dremio co-govern roadmap. Commercial interests could diverge from community needs even under TLP
  • Gravitino closing the gap — Gravitino v1.2 has credential vending, RBAC, and Iceberg REST. If Gravitino matures its Iceberg REST service, Polaris’ advantage narrows
  • Lakekeeper as lightweight challenger — Rust-based, single-binary, same REST spec. Niche but growing
  • Unity Catalog convergence — Databricks moving toward full REST catalog compliance could reduce need for Polaris in Databricks shops
  • Iceberg-only bet — if Delta or Hudi gains market share vs Iceberg, Polaris’ single-format focus becomes a constraint
  • FGAC spec delay — REST FGAC spec has been in discussion 12+ months. If it stalls, column/row security dependency on external tools continues indefinitely
Polaris in one sentence: The most technically complete Iceberg REST catalog available — narrow focus, best credential vending, best spec compliance, now fully ASF-governed — the right choice for any pure-Iceberg estate where legacy federation is not required.
Apache Gravitino — Full SWOT
S
Strengths
  • ASF TLP (Jun 2025) — 9 months ahead of Polaris. First to demonstrate governance maturity
  • Multi-format federation — Iceberg, Hudi, Delta Lake (external v1.2), Paimon, Lance under one namespace. Unique in the catalog landscape
  • Catalog-of-catalogs (metalake) — federates HMS, MySQL, Kafka, HDFS, S3 alongside Iceberg. Critical for enterprises migrating from legacy systems
  • Kerberos native — best-fit for on-prem AD/Kerberos environments. No Keycloak bridge needed
  • Azure AD OAuth2 login (v1.0) — direct Entra ID integration
  • Hive 3 catalog support (v1.1) — register Hive 3 metastores directly; legacy data governed without migration
  • Table Maintenance Service (v1.2) — automatic compaction, snapshot expiry, cleanup built-in. No external tooling needed
  • Marquez lineage integration (v1.0) — built-in lineage without separate OpenLineage pipeline
  • 2,600+ GitHub stars, 130% growth — fastest community growth of any catalog in 2025
  • Multi-backend (MySQL/PostgreSQL/H2) — flexible persistence
  • AI-native roadmap — MCP server, Lance REST, Model Catalog. Positions Gravitino as metadata layer for AI data stacks
  • Scan planning offload (v1.2) — reduces client-side query latency for Spark/DuckDB
  • Redesigned Web UI (v1.2) — Polaris has no UI; Gravitino ships a full governance portal
  • More OSS features — table maintenance, lineage, UI all in open source; Polaris reserves these for commercial tier
W
Weaknesses
  • Datastrato concentration — despite TLP, Datastrato employees remain dominant contributors. PMC diversity less broad than Polaris (no Google, Microsoft, Confluent equivalents)
  • China-origin perception risk — Datastrato’s Chinese origins may trigger additional scrutiny under OSFI B-10 third-party risk. Not a technical issue, but a procurement reality at Canadian banks
  • Credential vending less mature — added later than Polaris; production validation at scale is more limited
  • Iceberg REST service is a wrapper — wraps the standard Iceberg library rather than native implementation. May lag on leading-edge spec features
  • Ambitious scope = complexity — TMS, MCP, Lance, ClickHouse, Delta, Paimon, vector stores — every feature is a maintenance surface
  • No managed SaaS equivalent to Snowflake Open Catalog — Datastrato commercial offering has limited enterprise reach
  • Databricks cloud burst less proven — less community testing and documentation vs Polaris path
  • Trino connector lacks CTAS — CREATE TABLE AS SELECT not yet supported in Gravitino Trino connector
  • No catalog-level column masking — view-level permissions in v1.2 but no column masking or row filtering. Privacera still required
  • Rapid release pace — v0.8 to v1.2 in 12 months. Velocity is positive, but banks need predictable, stable releases
O
Opportunities
  • Legacy migration bridge — for enterprises with HMS/Hive 3/MySQL metadata, Gravitino is the only open-source catalog that federates these alongside Iceberg without rip-and-replace
  • AI-native positioning — MCP server + Model Catalog + Lance REST uniquely positions Gravitino for enterprises building AI data stacks. No other open catalog has this combination
  • ABAC roadmap — attribute-based access control planned; when implemented, applies across all federated catalogs simultaneously via unified namespace
  • Delta Lake bridge from Unity Catalog — Delta external tables make Gravitino the natural cross-format governance layer for Databricks + on-prem Iceberg shops
  • Polaris federation mode — Gravitino can sit in front of Polaris, combining Polaris’ superior Iceberg REST with Gravitino’s federation. This is the RBC architecture
T
Threats
  • Datastrato commercial risk — if Datastrato faces financial difficulty, the contributor base could fragment. Less backstop than Polaris’ dual-vendor Snowflake/Dremio model
  • Scope fragmentation — trying to be the catalog for AI models, vector data, Delta, Hudi, Kafka, and Iceberg risks delivering nothing great vs Polaris delivering one thing exceptionally
  • Polaris federation feature — Polaris v1.3 introduced catalog federation. If Polaris can federate Gravitino, the need to run Gravitino standalone diminishes
  • Security team perception — Datastrato origins + rapid release cadence + broad scope may trigger caution from enterprise security reviewers
  • HMS bridge becomes commoditised — as enterprises complete Iceberg migrations, the HMS federation differentiator erodes
  • Iceberg FGAC spec — if Polaris implements catalog-native column security first (as likely given spec co-authorship), Gravitino’s feature gap in this area widens
Gravitino in one sentence: The most capable multi-format federation layer in the open catalog landscape — uniquely qualified for enterprises governing Iceberg alongside legacy Hive, Delta, Kafka, and AI models — but that breadth comes with complexity, a concentrated contributor base, and an ambitious roadmap that may outpace operational maturity.

Are They Truly Open Source?
Polaris Open Source Assessment
✓ Apache 2.0 — fully permissive, can fork freely
✓ ASF TLP — vendor cannot unilaterally change license or direction
✓ IP donated to ASF — Snowflake donated the trademark
⚠ Open core risk — key enterprise features (compaction, lineage, governance) only in Dremio/Snowflake commercial products. OSS Polaris is the engine; enterprise features are the commercial moat
✓ ASF graduation process — demonstrated community health, vendor neutrality, release independence
Gravitino Open Source Assessment
✓ Apache 2.0 — fully permissive
✓ ASF TLP — graduated June 2025
⚠ Datastrato concentration — single commercial entity drives most commits
✓ More features in OSS — table maintenance, lineage, web UI all in the open-source release; not reserved for a commercial tier like Polaris
⚠ China-origin perception — not a legal issue (Apache 2.0 is Apache 2.0) but may require additional procurement scrutiny under OSFI B-10 at RBC specifically
Both carry "open source theatre" risk: Polaris’s most production-ready deployments (Snowflake Open Catalog, Dremio Open Catalog) are commercial with proprietary add-ons. Gravitino’s main backer (Datastrato) has limited enterprise reach. Under Apache 2.0, both projects give RBC the right to self-host, audit code, and avoid vendor lock-in — the risk is commercial concentration, not license terms.
RBC Recommendation
Primary Recommendation: Apache Polaris
For RBC’s architecture — pure Iceberg V2, no Teradata OTF dependency, cloud burst to Snowflake and Databricks, Privacera for security — Apache Polaris is the correct primary catalog. Removing OTF eliminated the only meaningful gap Polaris had. What remains is the most complete Iceberg REST implementation available, with the best credential vending, the best cloud burst story (Snowflake Open Catalog = zero-config), and now ASF TLP governance.

The February 2026 graduation resolves the biggest concern from earlier in this research cycle. Polaris is no longer incubating. It is a full Apache project with Snowflake, Dremio, Google, Microsoft, and Confluent on the PMC. Bloomberg is a committer, implying financial services production use. This is now a defensible enterprise architectural commitment.
Secondary Role: Gravitino as Migration Bridge (if needed)
Gravitino remains relevant for RBC in one specific scenario: if the HMS migration from legacy Cloudera/Hive tables is a multi-year programme, Gravitino as a federation layer presents a unified Polaris+HMS namespace to engines and Privacera without requiring migration to complete before production go-live.

Once the migration is complete, Gravitino can be removed — Polaris stands alone. If there is no meaningful HMS migration, Gravitino adds complexity without value. Deploy Polaris only.
