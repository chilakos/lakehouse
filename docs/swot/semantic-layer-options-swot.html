Semantic Layer Options — SWOT Analysis

Four options for the programmatic/agent semantic layer alongside Fabric (confirmed as BI/AI surface). Evaluated against RBC’s on-prem Trino + Polaris + Iceberg stack, Python transforms (not dbt), Tableau, and OSFI data sovereignty requirements.

✓ Fabric confirmed — BI/AI semantic layer (ADR-010) Cube.dev retired Python transforms · no dbt · ADR-005 Trino on-prem OCP · Polaris · MinIO Research: April 2026
Context: Fabric is confirmed as the BI/AI semantic layer (ADR-010). The question is what, if anything, covers the programmatic/agent access path — Tableau, ML pipelines, AI agents, and any consumer that needs real-time Iceberg access or complex analytical SQL that DAX cannot express. Cube.dev is being retired. These four options replace it or eliminate the need for a replacement.
Four options evaluated
Option A — No secondary layer
Retire Cube. Fabric is the only semantic layer. Tableau connects directly to Trino via JDBC. ML pipelines and agents use parameterised Trino SQL through a certified query pattern. No additional tooling.
Option B — AtScale
Universal headless semantic layer. GigaOm 2025 Leader. Works with Trino, Iceberg, Tableau, and Power BI. On-prem deployment supported. Snowflake-led financing. Financial services focus. Presents metrics as OLAP cubes without changing end-user workflows.
Option C — Starburst (Trino Enterprise)
Enterprise product built on top of Trino. RBC already runs OSS Trino — Starburst is an upgrade path, not a new component. Adds semantic views, data products, governance, and a catalog UI on the existing query engine.
Option D — dbt Semantic Layer (MetricFlow)
MetricFlow-powered metric definitions in YAML, exposed via REST/GraphQL. Most widely adopted vendor-neutral approach in 2026. Problem: requires dbt Cloud (not Core) and creates a dual-stack with RBC’s Python-only transform pipeline (ADR-005).
Option A — No Secondary Semantic Layer
Retire Cube. Fabric only. Tableau and agents use Trino directly.
S
Strengths
  • Lowest complexity — one less component to operate, secure, and upgrade
  • No additional vendor contract, licensing, or OSFI third-party risk review
  • Fabric handles all metric governance for BI consumers — that’s where 80% of consumption happens
  • Tableau analysts already write SQL against Teradata today — Trino JDBC is a natural migration
  • ML pipelines and agents get real-time Iceberg data without refresh lag
  • Certified query pattern (parameterised SQL) through a thin API layer already satisfies OSFI B-13 audit requirements
  • Removes the metric definition maintenance problem — single source of truth is Fabric DAX
  • Industry precedent: 35% of data teams operate without a dedicated semantic layer
W
Weaknesses
  • Metric drift risk — Tableau analysts build ad-hoc SQL; same KPI defined differently in Tableau and Power BI
  • No governed business language for Tableau — analysts must understand Gold table schemas directly
  • AI agents querying Trino directly must understand raw schema — no business-meaning layer for NL queries on the Trino path
  • No caching layer — every Tableau query hits Trino and Iceberg; complex queries at peak times compete with ETL workloads
  • Harder to scale governance — access control via Privacera/Trino, but no metric-level lineage for BCBS 239
  • If RBC Assist needs to answer complex multi-hop questions that DAX cannot express, there is no governed fallback path
O
Opportunities
  • Start simple, add a semantic layer later when the specific gap is validated by usage data — defer the decision with low cost
  • Polaris v1.3 catalog federation can expose governed views as pseudo-semantic definitions
  • Tableau Semantic Model (Tableau’s own published data sources) provides lightweight metric governance within Tableau without a separate tool
  • FastAPI certified query pattern scales well — add new certified patterns incrementally as agent use cases are validated
T
Threats
  • Metric drift becomes visible in audit — BCBS 239 examination asks “how is this number calculated?” and gets different answers from Tableau vs Power BI
  • AI agent failures at scale — agents writing free SQL against raw Gold tables without semantic context produce wrong answers without a semantic guardrail
  • Technical debt compounds — the longer there is no governed programmatic semantic layer, the more ad-hoc SQL queries accumulate in Tableau and Python notebooks
  • Eventual re-platforming cost — if metric drift becomes a problem in 12–18 months, migrating to AtScale or Starburst requires refactoring all Tableau data sources
When Option A is the right answer: If Tableau is used primarily for ad-hoc exploration and certified management reporting lives in Power BI, the metric drift risk is low. If any Tableau reports are used in regulatory submissions or executive scorecards, the lack of governed metric definitions is a material BCBS 239 risk.
Option B — AtScale
Universal headless semantic layer · GigaOm 2025 Leader · on-prem supported · Snowflake-led financing
S
Strengths
  • GigaOm 2025 Radar Leader — recognised for enterprise governance and rapid innovation in the semantic layer category
  • Financial services focus — specific FS use cases, MDX/OLAP cube presentation familiar to RBC’s existing Excel and SSAS users
  • On-prem deployment supported — compliance-heavy environments explicitly called out. OSFI B-10 risk is manageable
  • Snowflake-led financing — strategically aligned with RBC’s Snowflake cloud burst path via Polaris Open Catalog
  • Works with Trino, Iceberg, Tableau, Power BI, Excel, and Databricks — covers every consumer in RBC’s estate
  • Metrics defined once in AtScale, served to both Fabric (via connector) and Tableau — eliminates metric drift
  • Universal semantic layer does not replace Fabric — sits alongside it, serving consumers Fabric doesn’t reach cleanly
  • Adaptive aggregates — AtScale materialises pre-aggregations on Trino/Iceberg, reducing query latency for Tableau dashboards without a full Import copy
  • Forrester Total Economic Impact study: 551% ROI, two-month payback period (2025)
W
Weaknesses
  • Implementation complexity — user reports flag AtScale as challenging to implement; historically built around Hadoop ecosystem patterns
  • Another vendor, another OSFI B-10 review, another contract — adds to procurement and security approval cycle
  • Metric definitions in AtScale + DAX in Fabric = two authoring environments. Requires strict governance to prevent drift between them
  • Snowflake ownership post-financing introduces a commercial dependency — roadmap may favour Snowflake integration over on-prem Trino
  • MDX/OLAP presentation model adds complexity for teams more comfortable with SQL — learning curve for RBC’s data engineering team
  • Pricing: enterprise licensing, not published. Requires procurement engagement before architecture commitment
O
Opportunities
  • Single metric registry across Fabric and Tableau — define NII, VaR, LCR once in AtScale; both platforms query the same definition. Directly addresses BCBS 239 consistency requirement
  • AtScale MCP server (2025) — AI agents connect to AtScale via MCP, consuming governed metrics without writing raw SQL. Directly relevant to RBC Assist complex query path
  • Snowflake alignment — if Snowflake cloud burst becomes the primary analytics path, AtScale’s Snowflake-led roadmap becomes a feature not a concern
  • Excel connectivity — MDX cube exposure to Excel gives risk and treasury users pivot-table access to governed Gold metrics without BI tool licensing
  • Open Semantic Interchange (OSI) participation — AtScale is contributing to the OSI standard; metric definitions may become portable across tools in 2026–2027
T
Threats
  • Snowflake acquisition risk — Snowflake-led financing may precede full acquisition. If AtScale becomes Snowflake-native only, the on-prem Trino path could be deprioritised
  • Three semantic layers emerges — if teams bypass AtScale for direct Trino queries anyway, you end up maintaining AtScale, Fabric, and ad-hoc SQL simultaneously
  • Implementation drag — if AtScale’s Hadoop legacy creates friction on a Trino/Iceberg stack, the POC could take longer than expected and delay Tableau migration from Teradata
  • OSI standardisation makes vendor-neutral YAML (MetricFlow) the industry default by 2027 — AtScale’s proprietary model could become less differentiated
Critical pre-commitment validation: Run a POC against RBC’s specific Trino/Polaris/MinIO stack. AtScale’s Hadoop origins have caused friction in modern lakehouse deployments. Validate adaptive aggregation performance on Gold Iceberg tables before architectural commitment. Confirm on-prem Kubernetes/OCP deployment is a supported and tested path.
Option C — Starburst (Trino Enterprise)
Upgrade path on existing Trino · adds semantic views + data products + governance · no new query engine
S
Strengths
  • Upgrade path, not a new component — RBC already runs OSS Trino. Starburst is the same query engine with enterprise features added. No new technology adoption risk
  • Semantic views on existing Gold tables — define governed virtual datasets directly in Starburst without a separate semantic layer service
  • Data products concept — Starburst’s data product layer creates governed, discoverable data assets that Tableau and agents consume without raw schema knowledge
  • Starburst Enterprise security (SEP) — enterprise-grade Ranger integration, RBAC, and audit already aligned with Privacera
  • Single vendor for query engine + semantic layer + governance — reduces the total vendor footprint
  • Tableau connector built-in — Tableau connects to Starburst via JDBC with built-in column descriptions and semantic metadata
  • Dremio co-created Apache Polaris — Starburst’s Polaris integration is first-class
  • One support contract covers Trino + semantic layer — operationally simpler than managing Trino OSS + AtScale separately
W
Weaknesses
  • Starburst semantic layer is lighter than AtScale — semantic views are governed SQL views, not a full OLAP metric modelling environment. No MDX, no adaptive aggregation
  • Commercial product for something currently free — RBC runs OSS Trino at no licensing cost. Starburst Enterprise adds significant licensing cost for features that may only be partially used
  • Metric definitions still live in Starburst + DAX in Fabric — two authoring environments, same drift risk as AtScale
  • No Excel/MDX connectivity — risk and treasury teams who work in Excel pivot tables need AtScale or a separate SSAS-compatible layer
  • Starburst roadmap driven by Databricks competition — product investment may prioritise cloud features over on-prem semantic layer depth
  • SEP (Starburst Enterprise Policy) vs Privacera overlap — RBC already evaluating Privacera/Trust3 AI. Running both creates policy governance complexity
O
Opportunities
  • Consolidate Trino OSS + semantic layer + governance into one supported platform — Gautam’s team gets enterprise SLA, support, and upgrade path for the core query engine
  • Data products as the programmatic trust boundary — Starburst data products can serve as the certified query registry, replacing the need for a custom FastAPI layer
  • Starburst + Polaris is a validated production combination — reference architectures exist for this stack
  • Galaxy (Starburst UI) as a data catalog supplement — provides data discovery and lineage on top of Gold Iceberg without a separate catalog tool
T
Threats
  • Vendor lock-in on the query engine — migrating from Starburst Enterprise back to OSS Trino or to another engine becomes harder once semantic views and data products are built on Starburst-specific features
  • Price escalation risk — Starburst is a VC-backed company; enterprise licensing costs have increased as the product matures. RBC’s usage at 1.5 PB scale could generate significant licensing cost
  • Privacera/SEP policy conflict — if both Starburst SEP and Privacera are in play, policy authority becomes ambiguous. One must be the system of record for access control
  • OSS Trino community advancement — Trino OSS ships features rapidly; Starburst Enterprise features lag OSS by 3–6 months while adding licensing cost
The key question for Starburst: Is the upgrade justified by the semantic layer feature set, or by the enterprise support SLA on Trino? If the primary motivation is getting enterprise support for Trino (not the semantic layer), that is a separate, more straightforward decision. Don’t buy Starburst for the semantic layer if the semantic views capability is not materially better than what OSS Trino provides today.
Option D — dbt Semantic Layer (MetricFlow)
Most widely adopted vendor-neutral approach · YAML in source control · requires dbt Cloud · conflicts with ADR-005
S
Strengths
  • Most widely adopted vendor-neutral semantic layer in 2026 — 18% market share, growing rapidly, de facto standard for dbt-native teams
  • Metrics as code in Git — YAML metric definitions live alongside data models in version control, PR reviewed, CI tested. The governance model RBC already uses for Python pipelines
  • OSI standard leadership — dbt Labs, Snowflake, and Salesforce are driving the Open Semantic Interchange standard. MetricFlow YAML may become the industry portability format
  • REST/GraphQL API — programmatic consumers call the dbt Cloud API to query any metric. Serves Tableau, agents, and ML pipelines from one endpoint
  • Apache-licensed MetricFlow engine — the computation core is open source. No proprietary lock-in on the modelling language
  • Trino adapter exists — MetricFlow can generate SQL for Trino, so the underlying query engine is compatible
W
Weaknesses
  • Requires dbt Cloud — the Semantic Layer API that BI tools and agents consume is dbt Cloud-only. Not available in dbt Core. Adds a SaaS dependency RBC doesn’t currently have
  • ADR-005 conflict — RBC uses Python for all transforms, not dbt. Running dbt only for the semantic layer creates a dual-stack: Python pipelines + dbt YAML metric definitions. Two codebases to maintain for transforms and metrics
  • No on-prem deployment — dbt Cloud is SaaS-only for the Semantic Layer API endpoint. MetricFlow OSS can run standalone but without the governed API layer. OSFI B-10 exposure for policy metadata
  • Team skill gap — RBC’s data engineering team is Python-native, not dbt-native. Adopting dbt YAML authoring for metrics only adds a learning curve without the broader dbt ecosystem benefits
  • No caching or pre-aggregation — MetricFlow generates SQL on demand. No adaptive aggregates like AtScale. Every query hits Trino at full cost
  • Metric definitions in dbt YAML + DAX in Fabric = two authoring environments with different syntax. Same drift risk as other options, but harder to justify given the skill gap
O
Opportunities
  • OSI standard convergence — if MetricFlow YAML becomes the industry standard by 2027, metric definitions written today in dbt format become portable to any consuming platform
  • Community ecosystem — the dbt community is the largest data engineering community. Tooling, integrations, and best practices are well-documented
  • If RBC ever revisits the Python-only transform decision, dbt adoption for the semantic layer provides a natural migration path to dbt transforms
T
Threats
  • ADR-005 creates direct architectural tension — introducing dbt for the semantic layer implicitly reopens the Python-vs-dbt decision for transforms. Mission creep is a real risk
  • dbt Cloud SaaS = OSFI B-10 review required — metric definitions (what is “net interest income”, which tables it reads) would live in a US-hosted SaaS. Policy metadata exposure, similar to the Privacera concern
  • Version instability — MetricFlow is at v0.x versioning despite GA status. dbt notes rapid evolution means minor versions may introduce breaking changes
  • Cost at scale — dbt Cloud Team/Enterprise pricing for a 150-person data org adds meaningful SaaS cost for a tool only used for the semantic layer endpoint
Honest assessment: dbt Semantic Layer is the right answer for teams already standardised on dbt. It is the wrong answer for RBC. ADR-005 chose Python precisely to avoid dbt dependency. Introducing dbt Cloud for the semantic layer alone contradicts that decision, creates a dual-stack, and adds a SaaS B-10 exposure. Option D should be deprioritised unless ADR-005 is explicitly revisited.

RBC Recommendation
Recommended: Start with Option A, evaluate AtScale if Tableau metric governance becomes a validated requirement
Retire Cube.dev. Make Fabric the only semantic layer. Tableau connects to Trino via JDBC. ML pipelines and agents use parameterised Trino through the certified query pattern (FastAPI or Cube’s existing REST endpoint as a thin pass-through while deprecating).

The reason to start here rather than jumping to AtScale is sequencing: the Tableau use case has not been validated post-Teradata migration. It is possible that most certified Tableau reporting migrates to Power BI as part of the OBIEE consolidation, leaving Tableau only for ad-hoc exploration. In that case, Option A is the permanent answer and AtScale would be unnecessary cost and complexity.

Revisit in 3–6 months when the Tableau migration scope is clear.
Trigger for AtScale (Option B): Tableau metric governance at scale
If Tableau is confirmed as a platform for certified management reporting — not just ad-hoc exploration — then the BCBS 239 metric consistency requirement kicks in and AtScale becomes the right answer. One metric definition served to both Fabric and Tableau eliminates the drift risk. The Snowflake alignment and financial services focus are genuine advantages. Run a POC against the Trino/Polaris/MinIO stack before committing.

Do not evaluate AtScale until the Tableau scope is known. Procurement and a POC before that is wasted effort.
Trigger for Starburst (Option C): Enterprise Trino SLA is the driver, not the semantic layer
If Gautam’s team needs an enterprise SLA and support contract for Trino — the query engine that everything routes through — Starburst makes sense. The semantic layer feature comes along for free in that context. But don’t buy Starburst primarily for the semantic layer; its semantic views are lighter than AtScale and the licensing cost is significant for what amounts to governed SQL views.
Option D (dbt): Not recommended
Direct conflict with ADR-005. Requires dbt Cloud SaaS with OSFI B-10 exposure. Dual-stack maintenance burden alongside Python transforms. No on-prem deployment option for the Semantic Layer API. Do not pursue unless ADR-005 is explicitly reopened.
Open question added to leadership questions list (Q-10): What is the confirmed scope of Tableau usage post-OBIEE migration — certified reporting or ad-hoc only? The answer determines whether a secondary semantic layer is required and which option is appropriate.
