DataStage Migration SWOT Analysis

Big-Bang vs Phased Python vs Parallel-Run

Decided | Decision: Phased Python Migration | 2026-03-14 | Prepared for: Leadership Review

Executive Summary
The DataStage-to-Python migration strategy was evaluated across three approaches: big-bang replacement, phased Python migration using the BasePipeline framework, and parallel-run with DataStage maintained alongside Python pipelines. The phased Python migration was selected based on its proven track record -- 5-10 pilot DataStage jobs have been successfully migrated, 480 tests pass in CI, and the BasePipeline framework provides a repeatable pattern for the remaining 300+ jobs.

The phased approach balances migration speed with risk management. Each job is classified by complexity, migrated individually with full test coverage, and validated against DataStage output before the original job is decommissioned. This eliminates the all-or-nothing risk of a big-bang approach while avoiding the indefinite dual-maintenance cost of parallel-run.

Recommendation
The Phased Python Migration is recommended and already in progress. The BasePipeline framework is proven (480 tests passing), pilot migrations are complete (5-10 DataStage jobs), and the complexity classification system enables prioritized migration of the remaining 300+ jobs.

Next steps: (1) Complete complexity classification of all 300+ DataStage jobs, (2) Prioritize high-value/low-complexity jobs for the next migration wave, (3) Establish parallel validation framework for medium/high-complexity jobs, (4) Target 50% job migration by end of Phase 2.

SWOT Overview

Strengths

  • S1: BasePipeline Framework Is Proven — The BasePipeline framework in etl/src/pipelines/ provides a standardized contract for all ETL pipelines: extract, transform, validate_schema, quality_check, write. This framework has been validated with 480 passing tests and 5-10 pilot DataStage job migrations.
  • S2: Python Is Testable and CI-Friendly — Unlike DataStage's proprietary runtime, Python pipelines are fully testable in CI with standard tooling. The existing CI pipeline runs ruff linting, pytest with unit and integration tests, and terraform validation on every commit.
  • S3: Airflow Orchestration Operational — Apache Airflow is operational for DAG dependency management, scheduling, and monitoring. The watermark-based incremental loading pattern enables efficient processing without full table scans.
  • S4: Phased Approach Reduces Risk — Each DataStage job is migrated individually with its own test suite, output validation against DataStage, and rollback capability. This eliminates the all-or-nothing risk of a big-bang migration.
  • S5: Iceberg-Native ETL Enables Medallion Quality — Python pipelines write directly to Iceberg tables through the Nessie REST catalog, enabling native Bronze/Silver/Gold quality progression with schema validation and quality checks at each layer transition.

Weaknesses

  • W1: Full Migration of 300+ Jobs Will Take Months — The remaining DataStage job inventory is substantial. Even with the proven BasePipeline framework, migrating 300+ jobs with full validation requires significant engineering effort spread across multiple quarters.
  • W2: Python Performance vs DataStage for Complex Transformations — Some complex DataStage transformations (multi-way joins, complex aggregations, COBOL data type handling) may require PySpark rather than plain Python for equivalent performance, adding complexity to the migration.
  • W3: Team Retraining from DataStage to Python/PySpark — Engineers experienced with DataStage's visual designer and proprietary transformation stages need retraining on Python, PySpark, and the BasePipeline framework. This creates a temporary productivity dip during transition.
  • W4: Loss of DataStage Metadata and Lineage — DataStage maintains its own metadata repository with job dependencies, data lineage, and impact analysis. This metadata must be replicated in the new stack (Marquez for lineage, OpenMetadata for catalog) during migration.

Opportunities

  • O1: Iceberg-Native ETL Enables Medallion Data Quality — Writing directly to Iceberg tables enables native schema evolution, partition management, and time travel capabilities that DataStage's traditional target formats cannot provide. Quality checks are embedded in the pipeline contract.
  • O2: COBOL Copybook Parsing Validated — The mainframe source connectivity pattern has been validated, including COBOL copybook parsing for mainframe data integration. This removes a key technical risk for the migration of mainframe-sourced DataStage jobs.
  • O3: Open-Source Stack Eliminates License Costs — Moving from IBM DataStage (proprietary licensing) to Python/PySpark/Airflow (open-source) eliminates annual license costs. The savings compound as more jobs are migrated.
  • O4: Unified Observability and Lineage — Python pipelines integrate with Marquez for lineage tracking and OpenMetadata for catalog enrichment, providing unified observability across all data assets rather than DataStage's siloed metadata repository.

Threats

  • T1: DataStage-Specific Transformations Without Direct Equivalent — Some DataStage transformation stages (Complex Flat File, Hierarchical Data, COBOL-specific stages) have specialized logic that requires careful reimplementation in Python. Direct translation is not always possible.
  • T2: Mainframe Connectivity Edge Cases — While core mainframe connectivity is validated, edge cases in COBOL data types (packed decimal variations, multi-occurrence groups, REDEFINES clauses) may surface during migration of specific DataStage jobs.
  • T3: Production Stability During Migration Window — Running both DataStage and Python pipelines during the migration period increases operational complexity and the risk of data inconsistency if both systems write to overlapping targets.
  • T4: Knowledge Concentration Risk — During early migration, BasePipeline expertise is concentrated in a small group of engineers. If key engineers leave, migration velocity drops.

Threats (4 items)

T1: DataStage-Specific Transformations Without Direct Equivalent

Some DataStage transformation stages (Complex Flat File, Hierarchical Data, COBOL-specific stages) have specialized logic that requires careful reimplementation in Python. Direct translation is not always possible.

Evidence: DataStage has 60+ proprietary transformation stages; some (Hierarchical Data, Complex Flat File) have no direct Python equivalent
Mitigation: Complexity classification in job inventory identifies high-risk jobs for early attention. High-complexity jobs are migrated last with extended validation periods. PySpark provides equivalent capabilities for most transformation patterns; specialized stages are reimplemented as Python functions with comprehensive test suites.

T2: Mainframe Connectivity Edge Cases

While core mainframe connectivity is validated, edge cases in COBOL data types (packed decimal variations, multi-occurrence groups, REDEFINES clauses) may surface during migration of specific DataStage jobs.

Evidence: Core mainframe patterns validated in Phase 2; edge cases in COBOL packed decimal, multi-occurrence groups, REDEFINES remain untested
Mitigation: Phase 2 validated core mainframe patterns; edge cases handled incrementally as they surface during job migration. COBOL copybook parser is extensible for new data types. Parallel validation against DataStage output catches any data type mismatches.

T3: Production Stability During Migration Window

Running both DataStage and Python pipelines during the migration period increases operational complexity and the risk of data inconsistency if both systems write to overlapping targets.

Evidence: Dual-running DataStage and Python pipelines during migration creates operational overhead and data consistency risk
Mitigation: Each job migration follows a strict protocol: Python pipeline runs in shadow mode (read-only validation) before DataStage decommission. Output comparison validates row counts, checksums, and business rule compliance. Decommission only after 2-week validation period with zero discrepancies.

T4: Knowledge Concentration Risk

During early migration, BasePipeline expertise is concentrated in a small group of engineers. If key engineers leave, migration velocity drops.

Evidence: Initial BasePipeline framework built by core team; knowledge concentration risk until broader team adoption
Mitigation: Comprehensive documentation in etl-patterns.md (565 lines) serves as onboarding reference for 40+ engineers. Pair programming and code review requirements ensure knowledge transfer. Each migration wave includes new engineers to broaden expertise.
