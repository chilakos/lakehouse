Data Model Strategy SWOT Analysis

Keep FSDM vs Evolve Incrementally vs New Medallion-Native Model

Undecided | 2026-03-14 | Prepared for: Leadership Review

Executive Summary
The lakehouse architecture currently uses a Financial Services Data Model (FSDM) that is partially aligned across Bronze, Silver, and Gold layers. The Gold layer has already evolved organically toward medallion naming conventions (gold.trading_metrics, gold.risk_exposure), while Bronze and Silver layers largely retain FSDM entity naming. This analysis evaluates whether to formalize this evolution, revert to strict FSDM, or redesign from scratch.

Three options are evaluated: (1) Keep FSDM as-is with strict adherence, (2) Evolve FSDM incrementally by preserving entity names in Bronze/Silver while formalizing medallion conventions in Gold, or (3) Break from FSDM entirely with a new medallion-native model. Option 2 is recommended as it formalizes the organic evolution already happening in the codebase while preserving backward compatibility and minimizing disruption to 40+ engineers.

Recommendation
We recommend Option 2: Evolve FSDM Incrementally. The codebase already shows organic evolution -- Gold tables use medallion naming (gold.trading_metrics, gold.risk_exposure) while Bronze and Silver retain FSDM conventions. Formalizing this pattern preserves the 40+ engineer team's existing knowledge, maintains backward compatibility for regulatory reporting, and enables data quality contracts per medallion tier.

The incremental approach means: Bronze/Silver layers keep FSDM entity names and add medallion quality metadata columns, Gold layer formalizes domain-driven naming with explicit ties to FSDM source entities, and a business glossary bridges FSDM terms to physical layer names. This is additive, not replacing -- no existing queries break.

Leadership should verify: (a) regulatory reporting queries can use compatibility views during transition so that audit queries continue to work unchanged, (b) business glossary mapping effort is acceptable (estimated 2-3 weeks for core entities), and (c) downstream consumers (BI dashboards, scheduled reports) can be migrated to use Gold layer names on the team's preferred timeline rather than requiring a coordinated cutover.

SWOT Overview

Strengths

  • S1: FSDM Provides Standardized Financial Services Vocabulary — The Financial Services Data Model covers Party, Account, Instrument, Transaction, Risk, and Compliance domains with industry-standard naming conventions. This vocabulary is understood across the organization and maps to regulatory reporting requirements.
  • S2: Gold Layer Already Uses Medallion Naming — The Gold layer has organically evolved to use medallion-style naming conventions (gold.trading_metrics, gold.risk_exposure) rather than strict FSDM entity naming. This de facto evolution demonstrates that the team naturally gravitates toward domain-driven names in the consumption layer.
  • S3: 40+ Engineers Already Know FSDM Conventions — The existing engineering team has years of experience with FSDM naming, entity relationships, and query patterns. This institutional knowledge is a significant asset that would be costly to replace.
  • S4: Medallion Layers Enable Clear Data Quality Contracts — The Bronze/Silver/Gold medallion architecture naturally supports data quality contracts at each tier: Bronze is raw with metadata, Silver is cleaned and deduplicated, Gold is curated and aggregated. This quality progression is independent of entity naming but enhanced by formalizing it.
  • S5: Incremental Evolution Already Proven in Practice — The current codebase demonstrates that incremental evolution works without breaking existing systems. Bronze and Silver tables retain FSDM naming while Gold tables use new names, and both patterns coexist in the same catalog and query engine.

Weaknesses

  • W1: FSDM Is Partially Followed — The current implementation is only partially aligned to FSDM, creating inconsistency. Some entities follow strict FSDM naming while others have drifted. This partial adherence means neither strict FSDM nor pure medallion conventions are fully realized.
  • W2: FSDM Is a Teradata-Proprietary Model — FSDM was designed by Teradata for relational data warehouse architectures. As the architecture shifts toward a lakehouse model and Teradata's role potentially diminishes, continued reliance on a Teradata-specific data model creates an implicit dependency.
  • W3: Strict FSDM Does Not Express Medallion Quality Tiers — FSDM entity definitions do not inherently express data quality tiers (raw vs cleaned vs curated). The medallion architecture's key value proposition -- explicit quality contracts per layer -- requires additional metadata that FSDM was not designed to convey.
  • W4: Mapping FSDM Entities to Medallion Layers Requires Metadata — To maintain FSDM naming while operating in a medallion architecture, an additional metadata layer is needed to map FSDM entities to their Bronze, Silver, and Gold incarnations. This adds complexity to the data catalog and governance tooling.

Opportunities

  • O1: Incremental Evolution Preserves Investment While Modernizing — Formalizing the organic evolution already underway (FSDM in Bronze/Silver, domain-driven in Gold) preserves the team's existing knowledge investment while establishing modern naming conventions in the consumption layer where business users interact most.
  • O2: Data Quality Contracts Per Medallion Tier — A formalized medallion naming convention enables explicit data quality SLAs per tier: Bronze guarantees completeness, Silver guarantees deduplication and type correctness, Gold guarantees business metric accuracy. These contracts can be monitored and enforced.
  • O3: Business Glossary Bridges FSDM Terms to Physical Names — A business glossary (already seeded in glossary-seed.json) can map FSDM business terms to physical layer names, enabling both business users and technical teams to find data using their preferred vocabulary. OpenMetadata supports glossary-driven discovery.
  • O4: Vendor Independence Through Layer Abstraction — By using medallion layer naming in Gold (the consumption layer) and abstracting FSDM to Bronze/Silver (the engineering layer), the architecture becomes less dependent on Teradata's FSDM model. If Teradata's role diminishes, Gold layer consumers are unaffected.

Threats

  • T1: Breaking Change Risk for 40+ Engineer Team — Any data model change risks breaking existing queries, dashboards, and automated reports across a 40+ engineer team. Even well-communicated changes create a period of confusion and increased support burden.
  • T2: Regulatory Reporting Queries Tied to FSDM Column Names — Regulatory reports (BCBS 239 compliance, risk reporting) may reference specific FSDM entity and column names. Changing these names could break regulatory query pipelines and require re-validation with compliance teams.
  • T3: Loss of FSDM Vendor Support — If the organization departs from strict FSDM adherence, Teradata's FSDM support and tooling (data model documentation, entity relationship diagrams, schema validation tools) become less applicable. The team must self-maintain any evolved model documentation.
  • T4: Scope Creep in Model Evolution — An incremental evolution approach could lose discipline over time, with different teams making inconsistent naming choices in the Gold layer. Without governance, the evolved model could become as inconsistent as the current partial FSDM adherence.
