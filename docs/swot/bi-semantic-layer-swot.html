BI Semantic Layer SWOT Analysis

Direct Access vs dbt Metrics vs AtScale vs Cube

Decided | Decision: Cube v0.36.0 | 2026-03-14 | Prepared for: Leadership Review

Executive Summary
The BI semantic layer evaluation compared four approaches for providing a unified metric definition layer between the lakehouse and BI consumers (Tableau, Power BI). Cube v0.36.0 was selected for its combination of unified metric governance, PostgreSQL wire protocol compatibility (enabling any SQL-speaking BI tool to connect), and pre-aggregation caching for query performance.

The trading_metrics and risk_exposure cubes are operational, defining measures with exact calculation logic that serves as the single source of truth across all BI consumers. The PostgreSQL wire protocol on port 15432 enables Tableau and Power BI to connect via standard PostgreSQL drivers, eliminating the need for specialized connectors.

Recommendation
Cube v0.36.0 is recommended and already operational. The trading_metrics and risk_exposure cubes demonstrate the pattern: YAML-defined measures with exact calculation logic, accessible via PostgreSQL wire protocol on port 15432. BI tools connect using standard PostgreSQL drivers -- no proprietary connectors required.

Key advantages over alternatives: dbt Metrics lacks a query serving layer (requires a separate tool for BI access), AtScale adds significant infrastructure complexity and license cost, and Direct Access provides no metric governance (each BI tool defines its own calculations, leading to definition drift).

SWOT Overview

Strengths

  • S1: Unified Metric Definitions in YAML — Cube provides a declarative YAML-based metric definition layer. The trading_metrics and risk_exposure cubes define measures (total_notional, trade_count, avg_price, total_market_value, total_var_95, etc.) with exact calculation logic, eliminating metric definition drift across BI tools.
  • S2: PostgreSQL Wire Protocol for Universal BI Compatibility — Cube exposes a SQL API via PostgreSQL wire protocol on port 15432. Any BI tool that can connect to PostgreSQL (which is virtually all of them) can query Cube without specialized connectors or plugins.
  • S3: Pre-Aggregation Layer for Performance — Cube's pre-aggregation feature caches frequently accessed query patterns, reducing load on the underlying Trino query engine and providing sub-second response times for dashboard queries.
  • S4: Open-Source with Commercial Support Available — Cube is open-source (MIT license) with an optional cloud-hosted version for teams wanting managed infrastructure. Self-hosted deployment is fully supported and already operational in the lakehouse stack.
  • S5: Business Glossary Term Linkage — Cube YAML definitions include metadata fields that map to business glossary terms, enabling business-friendly metric discovery. The glossary_term metadata on each measure bridges technical column names to business vocabulary.

Weaknesses

  • W1: Additional Infrastructure Component to Maintain — Cube adds another service to the infrastructure stack that requires monitoring, upgrades, and operational attention. It runs as a separate container (cube-api) with its own configuration and data store.
  • W2: Cube-Specific YAML Learning Curve — Teams need to learn Cube's YAML schema for defining cubes, measures, dimensions, and pre-aggregations. This is a new DSL that adds to the team's tooling vocabulary.
  • W3: Pre-Aggregation Configuration Requires Tuning — Effective pre-aggregation requires understanding query patterns to define the right rollup combinations. Misconfigured pre-aggregations waste storage and compute without improving query performance.

Opportunities

  • O1: Glossary Term Linkage Enables Business-Friendly Discovery — Cube YAML definitions map to business glossary terms via the meta.glossary_term field. This enables business users to discover metrics using familiar vocabulary rather than technical column names, bridging the gap between data engineering and business analysis.
  • O2: Caching Reduces Trino Query Load — Cube's pre-aggregation and result caching intercepts repeated dashboard queries before they reach Trino, reducing compute load on the lakehouse query engine and improving overall cluster utilization.
  • O3: Centralized Metric Governance Prevents BI Tool Drift — With Cube as the single metric definition layer, all BI tools compute the same metrics the same way. This eliminates the common problem of Tableau and Power BI showing different numbers for the same metric due to divergent calculation logic.
  • O4: Extensible to New Consumers Without Infrastructure Changes — Any new BI tool, reporting system, or ad-hoc query tool can connect to Cube via the PostgreSQL protocol. Adding a new consumer requires no infrastructure changes, just a standard database connection configuration.

Threats

  • T1: Cube Project Roadmap Changes — Cube is a venture-backed company (Cube Dev) that may change its open-source strategy, pricing model, or feature availability. Major open-source projects have historically changed license terms.
  • T2: Scaling Limitations for Concurrent BI Users — Under high concurrency (50+ simultaneous BI users), Cube's single-process architecture may require scaling configuration. Default deployment may not handle peak dashboard refresh loads.
  • T3: Trino Query Compatibility Edge Cases — Cube translates SQL queries to the underlying data source (Trino). Complex SQL patterns from BI tools may not always translate correctly, requiring custom SQL or measure definitions.
  • T4: Vendor Ecosystem Fragmentation — The semantic layer market is fragmented with multiple competing approaches (dbt Metrics, AtScale, Cube, Looker Modeling, Tableau Prep). Choosing Cube means investing in one ecosystem while alternatives continue evolving.
