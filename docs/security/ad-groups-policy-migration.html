AD Groups & Policy Migration

How existing RBC Active Directory groups carry over from Teradata to the Iceberg lakehouse. What changes is not who can access what — that stays in AD. What changes is how the access decision is enforced at query time.

✓ AD groups unchanged — lives in Active Directory Trust3 AI or Immuta sync from AD/LDAP Teradata GRANTs → Ranger policies or Immuta subscriptions Masking views — key migration risk
Core principle: The AD groups are the continuity thread. RBC’s IAM team maintains them today for Teradata access. They carry over to the lakehouse unchanged — same groups, same membership, same governance process. What changes is the tool that consumes those groups to make enforcement decisions at query time.
What exists in Teradata today
The Teradata access model is built on three layers working together:

AD groups (e.g. RBC-DATA-RISK-READ, RBC-DATA-FINANCE-PII-CLEARED, RBC-DATA-WHOLESALE-READ) — live in Active Directory, maintained by IAM. These are not Teradata constructs.

Teradata roles — mapped to AD groups via LDAP sync into Teradata’s security layer. When someone’s AD group changes, Teradata role membership updates automatically.

GRANT statements — GRANT SELECT ON fsdm_party TO ROLE rbc_risk_read — table-level access attached to roles.

Teradata masking views — many environments implement column-level security through database views that hide sensitive columns. v_fsdm_party_masked returns 'XXX-XXX-XXX' for SIN columns. These are security controls but invisible in the GRANT table.

The Teradata GRANT → Policy translation
This is a translation, not a redesign. The Teradata DBA team can export the current role-to-table grant matrix. That export becomes the source of truth for building the initial policy set. It is mechanical — the access model does not change, only the enforcement mechanism.

⚠ The critical migration risk — security-bearing Teradata views
The biggest migration gotcha: Many Teradata environments implement security through database views rather than explicit GRANTs. A view called v_fsdm_party_masked that hides SIN columns is a security control — but it is invisible in the GRANT table. If you replicate the GRANTs and miss the masking views, you will expose data that was previously hidden when you point Tableau or Trino at the new Iceberg tables.
Migration checklist
1. Export Teradata grant matrix
DBA team exports: all roles, all GRANT SELECT statements, all role-to-AD-group mappings. This is the source of truth for policy translation.
2. ⚠ Audit all Teradata views for security-bearing masking
JoAnn’s DA team must identify which Teradata views are security controls (hide columns, filter rows) vs convenience joins. Each security-bearing view must be mapped to an explicit column/row policy in Trust3 AI or Immuta BEFORE that Teradata table is decommissioned. This is the step most likely to be missed.
3. Configure AD/LDAP sync in Trust3 AI or Immuta
IAM team provides AD bind credentials. Configure sync schedule (15–30 min). Validate group membership is flowing correctly before any policy is activated.
4. Translate grants to policies (scriptable)
The grant export can be scripted into Ranger policy import format (Trust3 AI) or Immuta API calls. This is mechanical — the DA/platform team does not need to redesign the access model, just translate it.
5. Validate parity before Teradata decommission
For each AD group, run the same query against the Teradata table (via legacy path) and the new Iceberg table (via Trino + security tool). Column visibility and row counts must match. This is the gate that internal audit signs off on before Teradata tables are removed.
6. Run parallel for 30 days before cutover
Teradata and Iceberg access control run simultaneously. Any access discrepancy discovered during this period is caught before production cutover. Do not decommission Teradata tables until this parallel run is clean for 30 days.
