The inconvenient truth (unchanged): No single tool gives you unified column masking across Spark + Trino + Databricks + Teradata OTF + Fabric in one package. Microsoft Fabric's native security (DDM in SQL endpoint, RLS) only applies within Fabric's own query surface — it does not protect the same underlying Iceberg/Delta files when read by Trino, Spark, or Teradata OTF directly.
🔵 Key Fabric finding: Fabric has strong column masking via T-SQL Dynamic Data Masking (DDM) and Row-Level Security — but only through the SQL Analytics Endpoint. If your Fabric consumers are SQL-based (Power BI, T-SQL, DirectLake), this is mature and production-ready. If consumers are Fabric Spark notebooks reading Delta/Iceberg directly, DDM does not apply — you need OneLake RBAC (item-level only, no column masking) or an external tool like Purview DLP.
🔵 Microsoft Fabric — Column Security Deep Dive
Three distinct security surfaces inside Fabric — each works differently. Understanding which surface your consumer uses is critical.
Surface 1: SQL Analytics Endpoint
  • Column masking: T-SQL Dynamic Data Masking (DDM) — full, production-ready
  • Row filtering: Row-Level Security (RLS) via inline table-valued functions — full
  • Who uses it: Power BI (Import mode via SQL), T-SQL clients, DirectQuery via SQL
  • How to apply DDM: ALTER TABLE customers ALTER COLUMN sin_number ADD MASKED WITH (FUNCTION = 'partial(0,"XXX-XXX-",4)')
  • Identity: Entra ID (AAD) — maps directly from AD via Entra Connect
  • Audit: All SQL queries logged to Fabric audit log → forwarded to Purview Compliance portal
  • Limitation: DDM only enforced when data is queried via this SQL endpoint — NOT when Spark reads the same underlying Delta table directly
⚠️ DDM does NOT protect Delta files read by Spark notebooks or external Trino/Iceberg readers
Surface 2: Fabric Spark (Notebooks / Pipelines)
  • Column masking: ❌ Not natively supported via Spark in Fabric
  • Row filtering: ❌ Not natively supported
  • Access control: OneLake RBAC — workspace-level and item-level only (no column granularity)
  • What this means: A Spark notebook in Fabric with access to a Lakehouse can read ALL columns of ALL tables in that Lakehouse — DDM does not intercept Spark reads
  • Mitigation options:
  • → Use Fabric Workspace roles to restrict who can run notebooks
  • → Serve sensitive data only via SQL endpoint (not raw Lakehouse)
  • → Pre-mask columns at Gold layer via pipeline transformation
  • → Use Purview sensitivity labels to trigger DLP blocking rules
⚠️ This is the most significant gap in Fabric's column security story for regulated data
Surface 3: OneLake (Shortcut / Direct access)
  • Column masking: ❌ None — OneLake is object storage, not a query engine
  • Row filtering: ❌ None at storage level
  • Access control: OneLake RBAC — Workspace Member/Contributor/Viewer + item-level permissions
  • Shortcuts: OneLake shortcuts to your on-prem Iceberg (via ADLS/S3 bridge) inherit OneLake RBAC — no column security from the shortcut itself
  • Entra ID: ✅ Native — all OneLake access governed by Entra ID identities
  • ADR-010 relevance: Your established architecture (Gold in Delta/Fabric for BI surface) means Fabric consumers hit the SQL endpoint → DDM applies ✅
⚠️ Import mode (ADR-010) routes through SQL endpoint — DDM applies. DirectLake reads Delta files directly — DDM does NOT apply.
Microsoft Purview + Fabric — What it adds
What Purview adds to Fabric security
  • Sensitivity labels (PII, PCI, CONFIDENTIAL) applied to Fabric items
  • DLP policies — block/alert when PII data is exported outside Fabric
  • Data Map — catalog and lineage for Fabric assets
  • Compliance audit — unified audit logs across M365 + Fabric
  • Auto-classification of columns via built-in classifiers (SIN, credit card patterns)
What Purview does NOT do
  • Purview does NOT enforce column masking at query time
  • Sensitivity labels do not automatically mask data — they trigger DLP policies (block/allow), not masking functions
  • Purview cannot push masking rules to Trino, Spark on-prem, or Teradata OTF
  • Purview is a governance/classification tool — not a query-time enforcement engine

1. OPA — Open Policy Agent (Trino)
Best OSS option for Trino. No Spark or Fabric coverage natively.
✅ Strengths
  • 100% OSS, Apache 2.0, free
  • Production-proven at Bloomberg, US DoD
  • Policy-as-code in Git — auditable

  • Structured audit logs — better than OPA alone
  • Multi-tenant Spark session isolation
❌ Weaknesses
  • Spark-only — no Trino, Databricks, Fabric, or Teradata
  • No tag-based policies without Atlas+Ranger
  • Built-in policy UI less mature than Ranger Admin

This gives you column security across every engine in your stack today without waiting for Ranger, Polaris FGAC spec, or any unproven roadmap item.
