No longer relevant without Teradata OTF
How removing Teradata OTF changes the landscape: With OTF gone, the HMS bridge requirement disappears entirely. Gravitino's primary differentiator was that HMS bridge — without it, Gravitino is a capable but overengineered choice for a pure Iceberg workload. Polaris becomes the dominant answer: it has the most complete REST spec, the best credential vending for hybrid on-prem + cloud burst, and the cleanest Privacera integration. The only remaining question is whether you need Nessie's branching capability for WAP workflows.
🏔️ Apache Polaris — The Dominant Choice Without OTF
ASF Incubating · v1.3.0 · Recommended for all RBC engines
Why it wins cleanly now
  • The OTF constraint was Polaris's only gap
  • Without OTF: Polaris serves Spark, Trino, Databricks, and Snowflake via the same REST endpoint
  • Credential vending is Polaris's standout feature — scoped STS tokens for MinIO on-prem AND Snowflake/Databricks cloud burst over PrivateLink
  • Snowflake Open Catalog = managed Polaris in Snowflake — cloud burst is literally zero config
  • Single service, single PostgreSQL backend, Kubernetes HA
What to watch
  • Still ASF Incubating — target graduation mid-2026
  • No row/column security (Privacera owns this — not a gap in your design)
  • PostgreSQL only backend — ensure your PostgreSQL HA meets RBC DR requirements
  • Audit logging is catalog events only — Privacera owns the compliance audit
  • No branching — if WAP becomes a requirement, layer Nessie on top
Privacera integration (cleanest path)
  • Privacera calls Polaris REST API to sync schema: catalogs → namespaces → tables → columns
  • Sync is pull-based on a schedule — no push from Polaris needed
  • Polaris service account granted read-only access by Privacera's sync agent
  • Column hierarchy maps cleanly to Privacera's policy model
  • Single REST endpoint covers all tables — one sync covers the full lakehouse

🏔️ + 🌿 Polaris + Nessie — If You Need WAP Branching
Polaris = operational catalog · Nessie = branching layer for regulated data workflows
When this combination makes sense
  • Write-Audit-Publish (WAP): Write to a Nessie branch, run data quality / compliance checks (Soda, Great Expectations), merge to main only if passing — atomic, no consumers see partial data
  • Regulatory snapshots: Tag Nessie at month-end for BCBS 239 point-in-time reproduction
  • Multi-table atomic commits: Update 3 related Gold tables atomically via a single branch merge — impossible with Polaris alone
  • Rollback: Bad pipeline run? Reset to prior tag in seconds across all affected tables
Complexity cost
  • Two catalog services to run and operate
  • Engines need NessieCatalog client for branching workflows
  • REST catalog on Nessie is still experimental — validate Privacera sync works against Nessie REST before committing
  • Alternatively: use Polaris for all engines, Nessie only for the pipeline branching workflow, with tables promoted to Polaris at merge time
  • Nessie pre-1.0 stability risk
🔗 Apache Gravitino — Reduced Role Without OTF
Still useful if HMS legacy migration is a multi-year journey · ASF TLP is strongest governance
Still relevant because
  • You almost certainly have HMS today with existing tables — Gravitino can federate HMS + Polaris during migration
  • ASF TLP governance is the strongest of any catalog here — if Polaris fails to graduate, Gravitino is a safe fallback
  • Single service manages the entire catalog surface for Privacera sync
  • Dedicated Trino and Spark connectors are better tested than generic REST clients in some edge cases
Less compelling now
  • Without Teradata OTF, the HMS bridge is no longer required
  • Federation adds operational complexity for a pure Iceberg stack
  • Credential vending is less mature than Polaris — cloud burst is harder
  • Polaris is simpler, lighter, and more Iceberg-focused
  • Databricks cloud burst less tested through Gravitino than Polaris
Verdict — Teradata OTF removed
🥇
Apache Polaris (standalone)
Without Teradata OTF, Polaris is the clear winner. Best REST spec compliance, best credential vending for hybrid on-prem + cloud burst, cleanest Privacera schema sync, and zero-config Snowflake integration via Open Catalog. Runs as 2 Kubernetes replicas on OCP backed by PostgreSQL. Simple to operate. The only caveat is ASF Incubating status — target production deployment after graduation (mid-2026 roadmap) or run it now with Cloudera or Dremio enterprise support.
🥈
Polaris + Nessie
Add Nessie if Write-Audit-Publish workflows are a firm requirement for your Gold layer. Nessie's branching model directly addresses BCBS 239 data accuracy validation (write, validate, publish atomically). The extra operational complexity is justified only if you have concrete WAP requirements — don't add it speculatively. Validate Privacera schema sync against Nessie REST before committing.
🥉
Gravitino (if Polaris governance risk is a concern)
If Polaris's incubating status is unacceptable to your risk/architecture governance, Gravitino is the only ASF TLP-graduated alternative. It's a capable catalog, handles Spark and Trino well, and gives Privacera a clean REST sync endpoint. The tradeoff is less mature credential vending and a more complex operational footprint for a pure Iceberg workload.

Bottom line: Without Teradata OTF, this is a straightforward call. Deploy Polaris. It was always the best pure Iceberg catalog — the only reason to consider anything else was the OTF gap. That gap is gone. Run Polaris on OCP (2 replicas, PostgreSQL HA). Point all engines at it via REST. Point Privacera's schema sync at it. Add Nessie later if and when WAP branching becomes a concrete pipeline requirement.
