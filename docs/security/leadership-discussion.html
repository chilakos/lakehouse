Budget & Commercial Decisions
01 BUDGET
Do we commit to Privacera commercial licensing?
Privacera is our recommended authorization and masking platform covering Spark, Trino, and Databricks. The alternative is a fully open-source stack (OPA for Trino + Kyuubi for Spark) at no license cost, but with two policy languages and more operational complexity.
Options
ACommit to Privacera commercial — single policy UI, Databricks coverage, managed control plane. Budget approval needed.
BOSS-first (OPA + Kyuubi) — no license cost, full on-prem, but two policy engines to operate.
C90-day Privacera POC before commit — validate integration with Polaris schema sync and RBC AD before licensing.
Risk if deferred: Security architecture cannot be finalized without this decision. It blocks the POC start date.
02 BUDGET
Databricks vs Snowflake: which cloud burst gets funded first?
Both Databricks and Snowflake are in the architecture as cloud burst compute options. Both require separate commercial agreements and have different value propositions — Databricks for ML/AI workloads, Snowflake for SQL analytics with zero-config Polaris integration via Open Catalog.
Options
ASnowflake first — lower integration risk, Open Catalog = native Polaris, SQL-native consumers already exist.
BDatabricks first — AI/ML workloads are the priority; RBC Assist roadmap drives this decision.
CNeither yet — prove the on-prem lakehouse first before cloud burst spend.
Recommendation: Snowflake first, given zero-config Polaris integration and existing SQL consumer base.
03 BUDGET
PCI scope reduction via tokenization — is it a priority?
Tokenizing PANs (payment card numbers) removes the majority of data from PCI DSS scope, significantly reducing audit and compliance overhead. It requires either a Privacera tokenization add-on or a separate tool (Protegrity, Voltage). The savings in audit cost may exceed the tooling cost, but it requires a business case.
Options
ABuild business case — quantify audit cost reduction vs tooling investment. Present at next QBR.
BDefer — use DDM masking as the primary PCI control. Tokenization is a year-2 initiative.
Governance & Risk Decisions
04 RISK
Is Apache Polaris's incubating status an acceptable risk?
Polaris is our selected Iceberg catalog. It is still ASF Incubating — not yet a graduated top-level project. It has approximately 18 months of release history outside Snowflake's managed service. Graduation is targeted for mid-2026. The alternative is Gravitino (ASF TLP, graduated June 2025) which carries more operational complexity but stronger governance credentials.
Options
AAccept the risk — proceed with Polaris under Dremio or Snowflake enterprise support contract as mitigation.
BWait for graduation — delay production until Polaris graduates (est. mid-2026). Run POC in parallel.
CUse Gravitino — ASF TLP governance removes the risk, at the cost of a more complex deployment.
Risk: Architecture board may require ASF TLP status for a production catalog. This needs a documented risk acceptance if Option A is chosen.
05 RISK
Privacera SaaS control plane — does it satisfy OSFI B-10?
Privacera's control plane is US-hosted SaaS. Under OSFI Guideline B-10, any material technology service arrangement with a foreign provider requires a jurisdictional risk assessment, right-to-audit clauses, data portability, and exit assistance provisions. The data itself stays on-prem — only policy metadata touches the SaaS plane.
Options
AProceed — policy metadata is not sensitive data; B-10 review is manageable. Legal/compliance sign-off needed.
BRequest Privacera on-prem/VPC deployment — some vendors offer private control plane. Validate with Privacera sales.
CSwitch to OSS (OPA + Kyuubi) — fully on-prem, no B-10 exposure, at cost of operational complexity.
This needs Legal and Compliance input before contracting. Do not sign Privacera without B-10 assessment.
Architecture Decisions
06 ARCHITECTURE
Do we have a concrete requirement for WAP branching (Nessie)?
The Write-Audit-Publish pattern — write data to a branch, validate quality and compliance, then atomically publish to production — is architecturally compelling for regulated data. It requires adding Nessie to the stack. Nessie should not be added speculatively; it adds operational complexity and has pre-1.0 stability caveats.
Options
AYes — specific Gold layer pipelines require it. Scope which tables and add Nessie to Phase 1.
BNot yet — defer until a concrete pipeline requirement emerges. Polaris alone for Phase 1.
Recommendation: Defer unless a specific pipeline team can articulate the WAP requirement today.
07 ARCHITECTURE
Microsoft Purview vs Apache Atlas — or both?
Atlas handles PII/PCI classification for the on-prem catalog (tags feed into Privacera policies). Purview handles Fabric-side governance and auto-labelling within the M365 estate. Both are in the architecture, but there is overlap. Given RBC's existing M365/Fabric investment, should Purview expand to replace Atlas on-prem, or do they serve distinct domains?
Options
ABoth — Atlas for on-prem Iceberg classification (feeds Privacera), Purview for Fabric/M365 surface. Distinct domains.
BPurview only — consolidate on Purview if RBC already has M365 E5. Purview can scan on-prem via IR connector.
CAtlas only — lighter footprint, fully on-prem, native Privacera TagSync integration. Purview for Fabric only.
08 ARCHITECTURE
DirectLake access from Fabric Spark — how do we handle it?
ADR-010 confirms Import mode for BI consumers — DDM applies. But data scientists using Fabric Spark notebooks to read from the Gold Delta tables bypass the SQL endpoint and DDM entirely. There is currently no column masking for Fabric Spark notebook consumers of PII/PCI data.
Options
ARestrict Fabric Spark access — data scientists must use the SQL endpoint or use pre-masked Gold views. Workspace policy enforced.
BCreate a separate anonymised Gold layer for Fabric Spark consumers — PII stripped at pipeline time, not query time.
CExpand Privacera to Fabric Spark — evaluate Privacera's Lakehouse integration for Fabric. Not confirmed as supported today.
This must be resolved before data scientists get Fabric Spark access to any Gold tables containing PII or PCI data.
Strategic & Platform Decisions
09 STRATEGY
SIEM platform: Splunk, Elastic, or Microsoft Sentinel?
The architecture requires a SIEM for Privacera audit aggregation, automated PCI DSS 10.4.1 review, and OSFI B-13 forensics. RBC may already have one of these. Sentinel has a natural fit with the Fabric/M365 investment. Splunk is the most proven for regulated financial services. This is likely already decided at the enterprise level — we need the answer to confirm our audit forwarding design.
Options / Clarification needed
→What SIEM is currently deployed at RBC for enterprise security events? Use that.
→If no enterprise SIEM exists for data access audit: Splunk Enterprise Security is the recommended choice for PCI-regulated environments.
10 STRATEGY
HashiCorp Vault vs CyberArk for secrets and PAM?
The architecture requires secrets management (service credentials, encryption keys) and privileged access management (break-glass, admin session recording). HashiCorp Vault is the OSS-native choice for Kubernetes/OCP environments. CyberArk is the enterprise PAM leader and may already be deployed at RBC for other systems.
Options
AUse existing CyberArk deployment if available — integrate lakehouse service accounts into the existing PAM programme.
BHashiCorp Vault — native OCP integration, dynamic secrets, lower operational overhead for the lakehouse team.
CBoth — Vault for dynamic secrets and KMS, CyberArk for PAM (admin session recording, break-glass). Non-overlapping roles.
11 OPERATIONS
Non-production environments: when do we need synthetic data?
Under OSFI B-13, non-production environments (dev, test, UAT) should not contain production PII. The current state is unknown — if prod data is being used in non-prod today, this is a compliance gap. Synthetic data generation (Gretel.ai, Mostly AI, or a custom pipeline) eliminates this risk and unblocks developer access to realistic data.
Options
AImmediate audit — confirm whether prod PII exists in any non-prod lakehouse environment today. If yes, this is Tier 1 remediation.
BPlan synthetic data pipeline as part of lakehouse Phase 2 — required before developer self-serve access goes live.
If production data is in dev/test today this is an active OSFI B-13 gap. Needs immediate answer.
