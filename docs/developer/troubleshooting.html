Troubleshooting FAQ

Common issues and fixes for the lakehouse platform

Docker and Services

Spark executor OOM killed during large Bronze ingest
Fix: Increase Docker Desktop memory allocation to 8 GB minimum (16 GB recommended). In Docker Desktop: Settings -> Resources -> Memory. Then restart Docker and run docker compose down && docker compose up -d.
Why: Spark executors run inside Docker containers. The default 2 GB memory limit is insufficient for large Bronze ingests that buffer source data in memory before writing to Iceberg. Each Spark executor needs at least 2 GB, and with multiple executors plus the driver, 8 GB is the minimum.
Nessie health check fails on startup
Fix: Wait 30 seconds for PostgreSQL to initialize, then restart Nessie: docker compose restart nessie. Verify with curl http://localhost:19120/api/v2/config.
Why: Nessie depends on PostgreSQL for its version store backend. On first startup, PostgreSQL needs to initialize its data directory and run schema migrations. If Nessie starts its health check before PostgreSQL is ready, it reports unhealthy. The depends_on condition ensures ordering but the PostgreSQL healthcheck may pass before migrations complete.
Airflow webserver won't start or shows 'database not initialized'
Fix: The airflow-init container must complete first. Check its status: docker compose logs airflow-init. If it failed, remove volumes and retry: docker compose down -v && docker compose up -d.
Why: Airflow requires database schema initialization (airflow db init) before the webserver or scheduler can start. The airflow-init container runs this migration. If it fails (often due to PostgreSQL not being ready), downstream Airflow services cannot start.
Ranger Admin UI inaccessible at localhost:6080
Fix: Ranger has a strict startup chain: ZooKeeper -> Solr -> Ranger DB -> Ranger Admin. Restart in order: docker compose restart ranger-zk ranger-solr ranger-db ranger-admin. Wait 60 seconds between each.
Why: Ranger Admin depends on Solr for audit indexing and its own database for policy storage. Solr depends on ZooKeeper for coordination. If any service in the chain fails, Ranger Admin cannot initialize its plugin registry and returns connection errors.
MinIO bucket not found error when running pipelines
Fix: The minio-init container creates required buckets on first startup. Re-run it: docker compose up minio-init. Verify buckets exist: docker exec minio mc ls local/.
Why: Pipelines expect buckets like lakehouse-data and lakehouse-warehouse to exist. The minio-init container creates these via mc (MinIO Client) commands. If minio-init ran before MinIO was healthy, the bucket creation silently fails.

Query Engine

Spark JAR conflict: NoSuchMethodError in Iceberg operations
Fix: Clean rebuild of all containers: docker compose down -v && docker compose up -d. This removes cached JARs and forces fresh downloads.
Why: Iceberg Spark runtime JARs must match the Spark version exactly (e.g., iceberg-spark-runtime-3.5_2.12 for Spark 3.5). A cached older JAR version causes NoSuchMethodError when the Iceberg API has changed. The -v flag removes volumes including the Maven cache.
Trino queries fail after catalog config change
Fix: Restart Trino workers to pick up the new configuration: docker compose restart trino. Verify with docker exec trino trino --execute 'SHOW CATALOGS'.
Why: Trino loads catalog configurations at startup and does not hot-reload them. Changes to catalog properties files (e.g., lakehouse.properties pointing to Nessie) require a worker restart. The Trino coordinator caches catalog metadata and must be restarted to pick up changes.
Cube pre-aggregation build times out
Fix: Check Trino connectivity from the Cube container: docker exec cube-api curl -s http://trino:8080/v1/info. Verify the CUBE_DB_HOST environment variable is set to trino (Docker service name, not localhost).
Why: Cube pre-aggregations are built by querying Trino. If the Cube container cannot reach Trino (wrong host, network isolation, or Trino is down), the build query hangs until the timeout. The CUBE_DB_HOST must use the Docker Compose service name for internal networking.

ETL Pipeline

OpenMetadata ingestion workflow hangs or shows 'indexing' status
Fix: Check Elasticsearch health: docker exec elasticsearch curl -s http://localhost:9200/_cluster/health. If status is red, restart Elasticsearch: docker compose restart elasticsearch. Then retry the ingestion.
Why: OpenMetadata uses Elasticsearch for search indexing. When ingestion completes, metadata is sent to ES for indexing. If ES is unhealthy (disk pressure, memory issues), the indexing step blocks indefinitely. The ingestion workflow reports 'indexing' status but never completes.

Testing

pytest markers not recognized: 'Unknown pytest.mark.unit'
Fix: Ensure markers are registered in etl/pyproject.toml under [tool.pytest.ini_options]. The markers list must include all custom markers (unit, integration, slow, snowflake). Run from the etl/ directory so pytest finds pyproject.toml.
Why: The project uses --strict-markers which requires all markers to be explicitly registered. If you run pytest from the repository root instead of etl/, pytest does not find pyproject.toml and the markers are unregistered. Always cd etl before running tests.
