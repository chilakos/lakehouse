ETL Patterns Reference

Standardized patterns for the lakehouse Python/PySpark ETL framework

1. Medallion Architecture Overview

All data flows through three layers in the medallion architecture.

Name Type Description
Bronze layer Raw-as-is with metadata. Namespace: lakehouse.bronze.*. Full history retention.
Silver layer Cleaned, deduplicated, entity-centric. Namespace: lakehouse.silver.*. Full history retention.
Gold layer Pre-aggregated metrics and curated views. Namespace: lakehouse.gold.*. Full history retention.

Data Flow

End-to-end data flow through Bronze, Silver, and Gold layers with quality gates.

Name Type Description
Source to Bronze stage Raw ingestion with metadata columns (source_system, ingestion_ts, batch_id). Critical quality gate blocks bad data.
Bronze to Silver stage Deduplication and business rules applied. Critical quality gate validates entity integrity.
Silver to Gold stage Aggregation and curation for analytics consumers.

Namespace Convention and Metadata

Format: lakehouse.{layer}.{entity}. The lakehouse prefix is the Iceberg catalog name (Nessie REST catalog).

Name Type Description
source_system STRING Identifier for the data source (e.g., 'trading_platform'). Added to every Bronze table.
ingestion_ts TIMESTAMP Timestamp when the record was ingested. Added to every Bronze table.
batch_id STRING Unique identifier for the ingestion batch. Added to every Bronze table.

2. Creating a New Pipeline

All pipelines must extend BasePipeline from src.pipelines.base. This enforces the extract -> transform -> validate_schema -> quality_check -> write contract.

Name Type Description
Step 1: Extend BasePipeline step Create a class extending BasePipeline with a PipelineConfig specifying name, target_layer, target_table, target_schema, and quality_checks_path.
Step 2: Run the Pipeline step Call pipeline.execute() to run extract -> transform -> validate_schema -> quality_check -> write. Returns dict with rows_written and quality results.
Step 3: Add Quality Checks step Create a SodaCL YAML file (see Section 3) and reference it in PipelineConfig.quality_checks_path.
Step 4: Create Airflow DAG step Create a DAG file in etl/dags/ following the patterns in Section 4.

Pipeline Code Example

Minimal Bronze pipeline extending BasePipeline.

Name Type Description
BasePipeline class Abstract base class at src.pipelines.base. Provides extract/transform/validate_schema/quality_check/write contract.
PipelineConfig dataclass Frozen dataclass for pipeline configuration: name, target_layer, target_table, target_schema, quality_checks_path, critical_checks.
MedallionLayer enum Enum with BRONZE, SILVER, GOLD values. Determines target namespace prefix.
execute() method Entry point. Runs the full pipeline contract and returns {rows_written: int, quality: dict}.

3. Data Quality Integration

Quality checks use Soda Core with SodaCL YAML definitions. Each layer has its own checks file.

Name Type Description
Critical Checks gate Block pipeline progression. Use for: schema validation, PK null/unique, referential integrity. Raises QualityGateError on failure.
Advisory Checks gate Generate warnings, pipeline continues. Use for: completeness rates, range validation, outlier detection.
SodaCL YAML format Define checks in src/quality/checks/{layer}_{entity}.yml. Reference in PipelineConfig.quality_checks_path.
Quality Results dict Returned as {passed: bool, critical_failures: list, warnings: list, all_results: list}. Consumed by Grafana dashboards.

SodaCL Example

Example SodaCL YAML for Bronze quality checks.

Name Type Description
primary_key_not_null critical missing_count(id) = 0 -- Primary key must not be null.
primary_key_unique critical duplicate_count(id) = 0 -- Primary key must be unique.
schema_required_columns critical Schema check: fail when required columns missing (id, name, source_system).
name_completeness advisory missing_percent(name) < 5 -- Data completeness threshold.

4. Airflow DAG Patterns

Hybrid DAG design: source-specific Bronze/Silver DAGs, separate cross-source Gold DAGs.

Name Type Description
Source-specific DAG pattern One DAG per source, Bronze -> Silver. Example: bronze_silver_trades.
Cross-source Gold DAG pattern Separate DAG for aggregation across sources. Example: gold_trading_metrics.
Maintenance DAG pattern Weekly Iceberg maintenance (compaction, snapshot expiry). Example: iceberg_maintenance.
Quality Report DAG pattern Daily quality monitoring across all layers. Example: quality_monitoring_report.

DAG Configuration

Standard DAG defaults and schedule conventions.

Name Type Description
default_args config owner: data-engineering, retries: 3, retry_delay: 2min, exponential backoff enabled, max_retry_delay: 30min.
Bronze/Silver Schedule schedule 06:00-07:00 UTC. Early morning when source data is available.
Gold Schedule schedule 08:00 UTC. After Bronze/Silver pipelines complete.
Quality Report schedule 09:00 UTC. After all pipelines complete.
Maintenance schedule Sunday 02:00 UTC. Low-traffic window for Iceberg table optimization.

5. Incremental Loading

Two approaches for incremental loading: watermark-based for batch sources and CDC for real-time change capture.

Name Type Description
Watermark-Based pattern For sources without CDC. Uses IncrementalConfig with watermark_column, merge_keys, target_table. High-water mark read from Iceberg table metadata.
CDC (Debezium) pattern Real-time: Debezium captures DB2 logs, events land in Kafka, Spark Structured Streaming reads and applies MERGE INTO Iceberg tables.
MERGE INTO SQL Upsert pattern: MERGE INTO target USING source ON key WHEN MATCHED THEN UPDATE SET * WHEN NOT MATCHED THEN INSERT *.
merge_incremental() function Utility at src.pipelines.incremental. Handles temporary view creation and Spark SQL MERGE INTO automatically.

6. Mainframe Source Handling

Mainframe flat files use COBOL copybooks parsed by Cobrix, a Spark data source for EBCDIC encoding.

Name Type Description
MainframeBronzePipeline class At src.pipelines.bronze.mainframe_ingest. Takes data_path, copybook_path, source_system, batch_id. Cobrix derives schema from copybook at runtime.
Cobrix library Spark data source for COBOL copybooks. Handles EBCDIC encoding, packed decimal (COMP-3), and complex record layouts.
DB2 z/OS JDBC driver ibm_db Python driver for direct mainframe database access.
Error Handling pattern Graceful skip when Cobrix JAR unavailable (CobrixNotAvailableError). Unit tests use mock data; integration tests need real EBCDIC binary files.

7. Testing Patterns

Unit tests run without Spark or Docker. Integration tests require the full Docker stack.

Name Type Description
Unit Tests pattern Mock PySpark at module level with unittest.mock. Use @pytest.mark.unit. Test schemas via StructType assertions, classification/filtering logic directly.
Integration Tests pattern Require Docker services (Nessie, MinIO, Spark). Use @pytest.mark.integration. Use spark_session fixture from conftest.py.
Reconciliation pattern Use reconcile_table() from src.quality.reconciliation to validate migration accuracy. Checks row counts, checksums, key columns with configurable tolerance.
