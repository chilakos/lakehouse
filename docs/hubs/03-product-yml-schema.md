# 03 — `product.yml` — the authoring schema

This is the artifact the DMO touches. It is intentionally narrow: enough
structure to make the product reproducible and governed, but not so much
that it becomes a mini programming language. Everything not in this
schema is either generated by the framework or written as plain SQL.

## Annotated example

```yaml
# products/client_household_exposure/product.yml
# Authored by: WM DMO
# Reviewed by: Hub Steward
# ---------------------------------------------------------------

apiVersion: lumina.rbc.ca/v1
kind: DataProduct
metadata:
  name: client_household_exposure
  domain: wealth_management
  owner:
    primary: jane.doe@rbc.com
    backup: john.smith@rbc.com
    team: WM-DMO-Reporting
  classification: confidential          # public | internal | confidential | restricted
  pii: true                              # drives masking macros automatically
  regulatory_tags: [BCBS-239, OSFI-B13]
  description: >
    Aggregated exposure across all positions held by every client in a
    household. One row per household per business date.
  business_steward: maria.garcia@rbc.com
  technical_steward: jane.doe@rbc.com

sources:
  # Bronze tables (landed by Helios). Version-pinned for reproducibility.
  - name: bronze_positions
    ref: bronze.helios_positions
    version: ">=2026-01-01"
    freshness:
      warn_after: 6h
      error_after: 24h

  - name: bronze_accounts
    ref: bronze.helios_accounts
    version: ">=2026-01-01"

  # EDLH conformed dimension — read-only federated reference
  - name: dim_customer
    ref: edlh.dim_customer
    version: "~1.4"
    access: federated                    # framework manages extract; DMO sees Bronze

  # Teradata view via federated read (Trino → Snowpipe → Bronze)
  - name: td_household_map
    ref: teradata.wm_household_map_v
    version: latest
    access: federated

silver:
  models:
    - name: clients_clean
      sql_file: silver/clients_clean.sql
      materialization: table
      tests:
        - unique: client_id
        - not_null: [client_id, household_id]
        - relationships:
            to: dim_customer
            field: customer_id
    - name: positions_clean
      sql_file: silver/positions_clean.sql
      materialization: table
      tests:
        - not_null: [account_id, position_value]
        - accepted_range:
            column: position_value
            min: 0

gold:
  models:
    - name: household_exposure
      sql_file: gold/household_exposure.sql
      materialization: incremental
      incremental_strategy: merge
      unique_key: [household_id, business_date]
      tests:
        - unique:
            columns: [household_id, business_date]
        - not_null: [household_id, business_date, total_exposure_cad]

  schema:                                # column-level contract — published to catalog
    - name: household_id
      type: string
      description: Household identifier from WM household map
      pii: false
    - name: business_date
      type: date
      description: As-of date for the exposure snapshot
    - name: total_exposure_cad
      type: number(18,2)
      description: Sum of position market value in CAD across all members
    - name: member_count
      type: integer
    - name: load_ts
      type: timestamp_ntz
      description: Audit column; populated by framework

  refresh:
    schedule: "0 6 * * *"                # 06:00 daily
    timezone: America/Toronto
    sla:
      ready_by: "08:00"
      max_runtime_minutes: 30

publish:
  certified: true                        # registers in catalog as certified product
  consumers:                             # known downstream — drives lineage notifications
    - power_bi: WM_Advisor_Dashboard
    - data_agent: wm_household_agent
    - hub: pcb-hub                       # cross-hub consumption is governed
  contract:
    breaking_change_notice_days: 30
    deprecation_notice_days: 90
```

## Schema reference

Every field is either required (R), recommended (Rec), or optional (O).
Required fields fail CI if missing. Recommended fields produce a CI
warning and require Hub Steward override.

| Section | Field | Req | Purpose |
| --- | --- | --- | --- |
| `metadata` | `name` | R | Snake-case identifier; becomes the Gold schema/table base name |
| `metadata` | `domain` | R | Hub domain (`wealth_management`, `pcb`, `capital_markets`, etc.) |
| `metadata` | `owner.primary` / `owner.team` | R | On-call accountability; flows to PagerDuty rotation |
| `metadata` | `classification` | R | Drives masking, retention, and access policy |
| `metadata` | `pii` | R | Drives automatic application of PII-masking macros |
| `metadata` | `regulatory_tags` | Rec | BCBS-239, OSFI-B13, PIPEDA, etc. |
| `metadata` | `description` | R | Becomes the catalog description |
| `metadata` | `business_steward` | R | Business sign-off authority |
| `sources` | `ref` | R | Fully-qualified source identifier |
| `sources` | `version` | R | Semver-style pin; `latest` is allowed only for federated sources |
| `sources` | `access` | O | `federated` or `copied`. Default `copied` (Bronze). `federated` implies platform-managed extract via Trino. |
| `sources` | `freshness` | Rec | `warn_after` / `error_after`; framework checks before run |
| `silver.models` | `tests` | R | Minimum bar enforced by CI: at least one not_null + one uniqueness or referential test |
| `gold.models` | `incremental_strategy` | O | `merge` / `append` / `insert_overwrite`. Default `merge`. |
| `gold.models` | `unique_key` | R if incremental | Required for merge strategy |
| `gold.schema` | (all fields) | R | Column-level contract published to catalog. Breaking changes require notice period. |
| `gold.refresh` | `schedule`, `sla` | R | Cron + business SLA; framework alerts if SLA missed |
| `publish` | `certified` | R | `true` triggers catalog certification flow |
| `publish` | `consumers` | Rec | Known downstreams; drives change-notification fan-out |
| `publish` | `contract` | Rec | Defaults to 30-day breaking, 90-day deprecation if absent |

## Why this shape

The schema is deliberately the contract between the DMO and the platform.
Anything in `product.yml` is the DMO's responsibility. Everything else is
the framework's. If a DMO needs something the schema doesn't support,
that's a framework feature request, not a custom workaround.

This is the lever for keeping self-service self-service. If we let
escape hatches accumulate, the schema becomes optional and we drift back
to the spaghetti pattern.
