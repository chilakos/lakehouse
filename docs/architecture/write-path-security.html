Write Path: Raw → Bronze → Silver → Gold

How Python pipelines write data through the medallion layers, how Polaris credential vending controls storage access, and how Trust3 AI or Immuta enforce access policies at every query boundary. Written against the actual pipeline code in this repo.

Python pipelines · ADR-005 Polaris REST catalog MinIO STS credential vending Trust3 AI or Immuta enforcement Iceberg V2 · Parquet on MinIO
The key insight: Security tools (Trust3 AI / Immuta) do NOT sit in the write path. They enforce at query time when someone reads data. The write path is controlled by Polaris credential vending — the pipeline service account has write permission to specific Iceberg table prefixes and nothing else. This is a deliberate separation: governance enforces who can read; credential vending controls what can be written to.

Step 5 — Gold pipeline reads Silver, writes domain aggregates

Write targets: lakehouse.gold.trading_metrics, gold.risk_exposure, gold.customer_360
🔐
Credential vend: Polaris mints separate scoped tokens for each Gold table prefix. The Gold pipeline cannot write to silver/ — token is scoped to gold/trading_metrics/ only.
⏱
Snapshot tags: Month-end snapshots tagged in Polaris with regulatory_snapshot=2026-03-31. Immutable. Reproducible for OSFI examinations.

Core principle: Security tools enforce at query time (reads), not write time. Polaris credential vending controls writes. Trust3 AI or Immuta Ranger/SystemAccessControl plugins intercept queries and apply column masking and row filters before data reaches the caller.

The classification scan — automatic policy creation
When the Bronze pipeline writes new data, a post-write trigger fires a classification job:

Trust3 AI path: The Privacera scanner samples column values from the new Bronze table. It matches against 50+ built-in identifiers (SIN, PAN card numbers, account numbers, email, etc.). Matching columns are tagged pii=true or pci=true in the Ranger policy engine. A default-deny masking policy is automatically applied — the column is masked for all users until a policy author explicitly grants clear-text access to specific roles.

Immuta path: Immuta Identification runs inside Trino using TABLESAMPLE — data never leaves the engine. Tags applied via Immuta’s classification framework automatically trigger subscription policies. The column becomes a governed data source in Immuta — users must subscribe (declare purpose) to access it.

In both cases: The data engineer who wrote the Bronze table does not need to manually author any security policy. Classification and default protection is automatic.
🔐 What neither tool does — common misconceptions
They do not encrypt data at write time (that is MinIO AES-256 SSE-KMS, configured at the storage layer). Trust3 AI adds field-level encryption separately via Ranger KMS UDFs.
They do not control which pipeline can write to which table — that is Polaris RBAC + credential vending scoping the STS token to a specific S3 prefix.
They do not audit Parquet file reads at the storage layer — they audit at the query layer (Trino, Spark). Direct MinIO bucket access bypassing Trino would bypass Trust3 AI and Immuta enforcement. This is why the architecture disallows direct storage access — all reads must go through Trino (ADR-002).
Step 1 — Raw zone upload (no catalog, no Iceberg)
1
RawZoneManager.upload() — etl/src/ingestion/raw_zone.py
The pipeline authenticates to MinIO using a credential from Vault. No Polaris, no Iceberg. This is a plain S3 PUT operation against the raw bucket. The key is structured to be immutable and partition-friendly.
# Authenticate via Vault — pipeline service account
vault_client = hvac.Client(url=VAULT_ADDR, token=VAULT_TOKEN)
minio_creds = vault_client.secrets.kv.read_secret("lakehouse/minio/raw-writer")

# Upload binary-exact file — no transformation
s3 = boto3.client("s3",
    endpoint_url="https://minio.rbc.internal",
    aws_access_key_id=minio_creds["access_key"],
    aws_secret_access_key=minio_creds["secret_key"],
)
key = f"raw/mainframe/{source_system}/{business_date}/{filename}"
s3.upload_file(local_path, bucket="lakehouse-raw", key=key,
    ExtraArgs={"ObjectLockMode": "COMPLIANCE",
               "ObjectLockRetainUntilDate": retain_until})

# Record manifest — forensic anchor for OSFI
manifest = RawZoneFile(
    raw_path=f"s3://lakehouse-raw/{key}",
    md5_checksum=md5(file_bytes),
    arrival_ts=datetime.now(UTC).isoformat(),
    ...
)

TradesBronzePipeline.execute() — via BasePipeline
SparkSession is pre-configured with the Iceberg REST catalog pointing at Polaris. When Spark touches a table, Polaris validates the JWT and vends a scoped MinIO STS token automatically. The application code just writes SQL — credential vending is transparent.

    .config("spark.sql.catalog.lakehouse", "org.apache.iceberg.spark.SparkCatalog") \
    .config("spark.sql.catalog.lakehouse.type", "rest") \
    .config("spark.sql.catalog.lakehouse.uri", "https://polaris.rbc.internal") \
    .config("spark.sql.catalog.lakehouse.credential", jwt_token) \
    .getOrCreate()

Step 3 — Silver pipeline: read Bronze (security enforced), write Silver
3
TradesCleanPipeline — etl/src/pipelines/silver/trades_clean.py
When the Silver pipeline reads Bronze via Spark, the Trust3 AI Ranger plugin (or Immuta Spark policy) intercepts the read. If the ETL service account has PII access, columns are clear. If not, PAN numbers are masked even in the transform layer.
# READ Bronze — security plugin intercepts here
# Trust3 AI: Ranger plugin embedded in Spark Driver evaluates policy
# Immuta: Spark cluster bootstrap policy applies masking UDFs
bronze_df = spark.table("lakehouse.bronze.trades")
# If ETL service account lacks PII clearance:
# bronze_df["account_number"] → "XXXX-XXXX-XXXX-1234" (masked)
# bronze_df["account_number"] → actual value (if cleared)

# FSDM conformance transform
silver_df = bronze_df \
    .withColumnRenamed("trade_id", "financial_transaction_id") \
    .withColumn("party_id", resolve_party_id("account_number")) \
    .withColumn("effective_date", to_date("trade_date")) \
    .withColumn("row_hash", sha2(concat_ws("|", *key_cols), 256)) \
    .filter(col("status") != "CANCELLED")

# SCD Type 2 — mark superseded rows
silver_df = apply_scd2(spark, silver_df, "lakehouse.silver.fsdm_financial_transaction")

# WRITE Silver — Polaris vends new scoped token for silver/ prefix
silver_df.writeTo("lakehouse.silver.fsdm_financial_transaction").merge()
Step 4 — Gold pipeline: Trino SQL aggregation
4
Gold aggregation — Trino SQL (not Spark)
Gold pipelines can use Trino directly (ADR-002 / ADR-005). Trino reads Silver Iceberg tables, applies FGAC enforcement at the coordinator, then inserts into Gold. The Gold pipeline service account has SELECT on Silver and INSERT on Gold only.
-- Trino query executed by Gold pipeline service account
-- Trust3 AI Ranger plugin on Trino coordinator enforces FGAC
-- Immuta ImmutaSystemAccessControl on coordinator does the same

INSERT INTO lakehouse.gold.trading_metrics
SELECT
    account_id,
    DATE_TRUNC('month', trade_date) AS month,
    SUM(notional_amount) AS total_notional,
    COUNT(*) AS trade_count,
    SUM(pnl) AS total_pnl
FROM lakehouse.silver.fsdm_financial_transaction
WHERE effective_date >= CURRENT_DATE - INTERVAL '1' MONTH
  AND is_current = true
GROUP BY 1, 2;

-- Polaris atomically commits Gold snapshot
-- Month-end: tag snapshot for regulatory retention

The difference in the write/transform path is subtle but important. Both products enforce at query time. The difference is how and where they intercept, which affects how ETL pipelines experience the enforcement.

For the write path specifically: both products behave identically — they do not interfere with writes at all. The difference is entirely in how reads and queries are enforced. The choice between Trust3 AI and Immuta does not change any pipeline write code. It changes how policies are authored and how queries are intercepted at read time.
