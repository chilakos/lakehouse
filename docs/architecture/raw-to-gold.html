Raw Zone — Source Ingestion Immutable · Binary-Exact · 7-Year Retention

What lands here

All source files arrive in the raw zone before any processing. Files are stored binary-exact — no encoding conversion. EBCDIC bytes are preserved as-is. This layer satisfies SEC Rule 17a-4, FINRA 4370, and BCBS 239 source record retention requirements.

Transfer Mechanisms

  • SFTP — z/OS batch job GDG → Linux landing server → S3
  • Connect:Direct / NDM — bank-to-bank standard; deposits at local path identical to SFTP
  • AWS CLI — aws s3 cp / aws s3 sync for bulk back-fills and SRE runbooks
  • CDC — Debezium or custom change capture for operational DB sources

S3 Path Convention

s3://lakehouse-raw/raw/mainframe/{source}/{YYYY-MM-DD}/{filename}

Manifest co-located at: _manifest/{source}/{date}.jsonl

Key Controls

  • MD5 checksum computed before upload, stored in manifest + S3 metadata tag
  • S3 Object Lock (Compliance mode) — 7-year retention, no deletion
  • Lifecycle: Standard → Standard-IA (90d) → Glacier IR (1yr) → Deep Archive (3yr)
  • After CLI upload: register via IngestionManifest.register_file()
GUIDE Full AWS CLI commands, Connect:Direct post-step script, and Object Lock verification in docs/mainframe-ingestion.md
Bronze Layer — Raw Iceberg Landing Append-Only · Schema-on-Read · Immutable History

What happens here

Raw files are decoded (EBCDIC→Parquet via Cobrix for mainframe, passthrough for structured sources) and written as append-only Apache Iceberg V2 tables. No business rules. No deduplication. Bronze is the permanent historical record.

Transforms

  • Format conversion only: EBCDIC → typed Parquet columns
  • Metadata columns appended: source_system, ingestion_ts, batch_id
  • No filtering, no deduplication, no business rules

Quality Gate

  • Schema validation — required columns present and typed
  • PK not-null, PK unique within batch
  • Soda Core checks defined in etl/src/quality/checks/bronze_*.yml

Technology

  • Format: Apache Iceberg V2 on MinIO/S3
  • Catalog: Nessie — branch-per-load, Git-style versioning
  • ETL: Python (DataStage migration: ~12,000 jobs)
  • Decode: Cobrix spark-cobol_2.12:2.9.2 for EBCDIC
  • Orchestration: Apache Airflow DAG per source domain
  • Lineage: OpenLineage emitted at every step → Marquez

Governance

  • Gravitino policy labels applied at ingest (PII, Confidential, Restricted)
  • Labels push to Apache Ranger for column-level enforcement
  • Nessie branch merged on successful quality gate pass
Silver Layer — FSDM-Conformed Cleansed Records Deduplicated · Entity-Resolved · Ranger-Governed

What happens here

Bronze records are cleansed, deduplicated, and entity-resolved to conform to the Teradata Financial Services Data Model (FSDM). Silver is the canonical source of truth for all downstream Gold builds. All queries run via Trino (ADR-002 — mandatory gateway, no direct Spark).

Transforms

  • Type casting, null handling, valid-value range checks
  • Deduplication by PK (window function, keep latest)
  • SCD Type 2 for slowly-changing entities
  • FSDM entity conformance: Party, Account, Transaction, Instrument, Risk, Compliance

Technology

  • Query engine: Trino 479 — mandatory per ADR-002, no Spark on Silver
  • ETL: Python (no dbt — confirmed ADR)
  • Catalog: Nessie with Iceberg V2
  • Quality: Soda Core SodaCL — uniqueness, RI, range checks
  • Governance: Gravitino → Ranger, column masking, row-level RBAC
  • Lineage: OpenLineage → Marquez → OpenMetadata
ADR-002 Trino is the mandatory query gateway. No direct Spark SQL on Silver or Gold. All engine access routes through Trino for consistent audit logging and Ranger enforcement.
ADR-005 No Spark, Python ETL only. DataStage → Python migration (~12,000 jobs). Python is the sole transformation engine — testable, Git-native, debuggable without a cluster.
Gold Layer — Curated Business-Ready Analytics Teradata OTF · Trino · Iceberg V2 · Ranger ACL

What happens here

Multi-table joins across FSDM subject areas, pre-aggregation, and business rule application produce curated, denormalized wide tables optimised for analytics. Gold is the authoritative compute-plane source: queried by Trino, Teradata Vantage (OTF), and the Cube NL-to-SQL layer.

Transforms

  • Multi-table FSDM joins: Party × Account × Transaction × Instrument
  • Aggregations: daily, MTD, YTD, rolling windows
  • Enrichment: market data overlays, risk calculations, compliance flags
  • Denormalization for analytics performance

Technology

  • Teradata Vantage — OTF/Iceberg engine, primary aggregation compute
  • Trino — cross-domain Gold joins, ADR-002 mandatory gateway
  • Format: Iceberg V2 on MinIO/S3, stable paths enforced
  • Maintenance: OPTIMIZE + VACUUM on schedule (Airflow DAG)
  • Code: GitHub — all ETL versioned, PR reviews, ADR log
  • Security: Ranger — authoritative ACL for all compute consumers

Cube Semantic Layer (NL-to-SQL path)

  • YAML metric definitions over Gold tables (trading_metrics, risk_exposure)
  • PostgreSQL wire protocol on :15432 for any SQL-speaking tool
  • RASL vector retrieval scales to 200+ Cube-modelled tables (ADR-006)
  • Feeds NL-to-SQL engine: Claude on AWS Bedrock (ADR-009)
ADR-001 Teradata Vantage as Iceberg OTF engine. Teradata is decoupled from storage — it reads Iceberg V2 files in S3/MinIO via Open Table Format. Compute and storage are separated.
ADR-006 RASL for NL-to-SQL at scale. pgvector schema linking replaces full-schema prompt stuffing. Scales from 2 to 200+ Cube-modelled Gold tables with 90%/70% accuracy thresholds on simple/complex queries.
Fabric Semantic Layer — BI & AI Surface Import Mode · VertiPaq · DAX · Prep for AI · ADR-010

Dual-Gold Design Decision

Gold exists in two deliberate representations. The Iceberg on-prem copy (above) is the authoritative compute plane, governed by Ranger. A separate Python ETL job copies curated Gold tables to Microsoft Fabric as Delta (V-Order optimised for VertiPaq). A Fabric Import semantic model reads this copy. No OneLake shortcuts. No XTable metadata virtualization. No OPDG agents. See ADR-010 for full rationale.

Python ETL Copy (Gold → Fabric)

  • Runs as Airflow DAG: gold_to_fabric_copy after Gold refresh
  • Reads Gold Iceberg via PyIceberg or Trino → Pandas
  • Writes Delta to Fabric OneLake Tables section
  • V-Order applied: VertiPaq-optimised sort and compression
  • Gold-layer tables only — not Bronze or Silver

Fabric Import Semantic Model

  • Mode: Import — VertiPaq in-memory, fastest query path
  • DAX measures, relationships, KPIs defined once, reused everywhere
  • RLS at semantic model layer (not OneLake security layer)
  • "Prep for AI" — AI Data Schema, Verified Answers, AI Instructions
  • NL2DAX via Fabric Data Agent → published REST endpoint

Why Import over Direct Lake

  • Fastest query performance — full VertiPaq in-memory
  • "Prep for AI" only available in Import (not Direct Lake)
  • RLS is cleanest at semantic model layer with no shortcut path failures
  • No XTable fidelity risk, no Iceberg partition compatibility issues
  • Gold is pre-aggregated — fits in Fabric capacity memory

Fabric SKU Guidance

  • F32 — minimum for production BI
  • F64 — recommended for 1,000+ reports / ~150 concurrent users
  • F128 — quarter-end and regulatory reporting peaks
ADR-010 Fabric Import semantic model as BI/AI surface. Supersedes the ADR-008 "Contingency" pattern. No OneLake shortcuts. No XTable. Dual-Gold is intentional. Full decision at docs/adr/010-fabric-import-semantic-layer.md.
ADR-008 OneLake shortcuts and XTable not adopted. S3-compatible shortcuts require key/secret auth only, XTable has partition fidelity gaps, RLS on cross-workspace shortcut paths returns 403. Full analysis at docs/adr/008-onelake-evaluation.md.

Consumption Layer — BI & AI Surfaces

One Fabric Import semantic model powers three consumption surfaces. DAX measures are defined once and shared across all three. RLS is enforced uniformly.

Power BI
  • Connects via Import semantic model (VertiPaq)
  • 1,000+ OBIEE reports migrating to certified datasets
  • Near import-mode query speed — no Trino round-trip per visual
  • DAX time intelligence, semi-additive measures, financial calculations
  • RLS enforced at semantic model layer
  • Copilot in Power BI active and grounded by semantic model
Tableau
  • Connects via Fabric XMLA endpoint — same semantic model as Power BI
  • Consistent KPIs across both BI tools — no definition drift
  • No separate Tableau data source or extract to maintain
  • RLS and CLS inherited from semantic model
  • WebFOCUS migration also routed through Fabric semantic model
RBC Assist (AI Chatbot)
  • Fabric Data Agent generates NL2DAX against semantic model
  • Published as REST endpoint from Fabric workspace
  • Azure AI Foundry wraps it as MicrosoftFabricPreviewTool
  • RBC Assist calls Foundry → Data Agent → DAX → structured answer
  • Entra ID identity propagated end-to-end — per-user RLS enforced
  • Only schema/metadata sent to Azure OpenAI — raw data never leaves RBC

Cross-Cutting Concerns

Governance Plane
  • Gravitino — unified policy authoring plane; one policy definition pushed to all engines
  • Apache Ranger — enforcement engine; column masking, row-level RBAC, audit trail
  • Nessie — catalog versioning; branch-per-load, Git-style table history and rollback
  • OpenMetadata — data discovery, classification, business glossary (v1.6.0)
  • Microsoft Purview — discovery + lineage on ADLS/Fabric surface (cloud plane)
  • OSFI B-13 / BCBS 239 — lineage auditability from source to consumer
Lineage & Quality
  • OpenLineage — provenance emitted at every transformation step
  • Marquez — OpenLineage server + web UI (:5000 / :3000)
  • Soda Core SodaCL — quality gate checks at Bronze and Silver
  • Airflow SLA alerts — pipeline failure notifications per domain
  • Gold OPTIMIZE + VACUUM — enforced on schedule; required for Fabric Delta copy fidelity
  • Schema evolution — tracked via Nessie catalog; non-breaking changes only
Monitoring & Delivery
  • Grafana + Prometheus — pipeline observability dashboards (:3001 / :9090)
  • StatsD exporter — Airflow metrics bridge to Prometheus (:9102)
  • Grafana Reporter — scheduled PDF report delivery (:8686)
  • GitHub — all ETL code, ADRs, config versioned; PR reviews enforced
  • Python ETL — no dbt, no Spark; sole transform engine (ADR-005)
  • GitHub Actions — CI/CD across dev / staging / prod environments
