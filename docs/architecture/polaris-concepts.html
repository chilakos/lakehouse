Polaris: Credential Vending & Native REST Catalog Explained

Two concepts that often get confused. What credential vending actually does. Why Polaris is not "just" the Iceberg REST spec. What you get with Polaris that you don't get with a bare REST catalog.

What is Credential Vending?
The short version: instead of giving your engine a permanent storage key, the catalog mints a temporary, scoped token just-in-time for the specific table being queried — and that token expires in minutes.
The problem it solves — without credential vending
⚠ Without credential vending — the dangerous way
In a naive setup, every compute engine (Spark, Trino, Databricks) needs to read Parquet files from your object store (MinIO, S3). The only way to do that is to give each engine a long-lived storage credential — an AWS Access Key, a MinIO access key, or a storage account key. This means:

• Every Spark node, every Trino worker has a copy of the master storage key in its config
• That key can access every file in the bucket — not just the table the user requested
• If the key leaks (config file, log output, memory dump), the entire data lake is exposed
• The key doesn't expire — a leaked key is valid until manually rotated
• You have no way to enforce "this Trino job may only read finance/customers/" at the storage layer

For PCI and OSFI environments, storing a master storage credential in engine configuration is unacceptable.
How credential vending fixes it
The credential vending flow — what happens when Trino queries a table
1
Engine authenticates to Polaris (OAuth2 JWT)
Trino presents its service account JWT token (issued by Keycloak from AD). Polaris validates the token. No storage credentials involved yet — just identity.
2
Engine requests table metadata from Polaris REST API
Trino calls GET /v1/catalogs/rbc/namespaces/finance/tables/customers Polaris checks: does this service principal have READ privilege on finance.customers? If no → 403. If yes → continue.
3
Polaris calls AWS STS / MinIO STS to mint a scoped credential
Polaris holds a single master IAM role or MinIO service account. It calls the STS (Security Token Service) endpoint and requests a temporary credential scoped to exactly the S3 prefix for this table: sts.assume_role( RoleArn="arn:aws:iam::account:role/polaris-storage", Policy={"Version":"2012-10-17","Statement":[{ "Effect":"Allow","Action":["s3:GetObject","s3:ListBucket"], "Resource":["arn:aws:s3:::lakehouse/finance/customers/*"] }]}, DurationSeconds=3600 # expires in 1 hour ) The result is a temporary AccessKeyId, SecretAccessKey, and SessionToken that only works for that one table prefix and expires in 1 hour.
4
Polaris returns metadata + vended credential to the engine
The REST response includes the table's metadata.json location AND the temporary credential: { "metadata-location": "s3://lakehouse/finance/customers/metadata/v23.metadata.json", "config": { "s3.access-key-id": "ASIA...", // temporary "s3.secret-access-key": "xyz...", // temporary "s3.session-token": "FwoGZXIvYXdzE...", // temporary "s3.region": "ca-central-1" } }
5
Engine reads Parquet files using the vended credential
Trino uses the temporary key to fetch metadata.json, then manifest files, then Parquet data. MinIO/S3 validates the token on each request. If Trino tries to access any path outside finance/customers/, the request is rejected — the token has no permissions there.
6
Token expires — no cleanup needed
After 1 hour (or whatever TTL was configured), the token automatically becomes invalid. Trino must request a new one for the next query. There is nothing to revoke, nothing to rotate, and no long-lived credential stored anywhere in the engine config.
What this means in practice
✓ What credential vending gives you
• No master key in engine config — Trino, Spark, Databricks hold zero long-lived storage credentials
• Least privilege at storage level — a vended token for finance/customers literally cannot read risk/trades
• Automatic expiry — leaked token is useless after TTL (1 hr by default)
• Auditability — every STS call is logged. You can see exactly which engine accessed which table path, when
• Works across clouds — Polaris vends S3 credentials for AWS, SAS tokens for Azure, OAuth2 for GCS, and STS tokens for MinIO on-prem. Same catalog API regardless of storage backend
• Blast radius control — compromise of a Trino worker node exposes one expired table-scoped token, not the entire data lake
⚠ What you need to set up
• MinIO STS endpoint must be enabled (MinIO ships this — just needs to be configured)
• Polaris needs one master role with broad storage access — this is the credential Polaris holds server-side to call STS with. Polaris should be the only service with this master role
• HashiCorp Vault should store Polaris's master credential (not in a config file)
• Bucket policy on MinIO should deny access to anyone except the Polaris service account and the STS-generated temporary tokens — this is the storage-level lock that makes the whole model work
One sentence: Credential vending means the catalog acts as a credential broker — engines never touch a long-lived storage key. They get a short-lived, table-scoped token minted just for their query and worthless an hour later. It's the difference between giving every employee a master key to the building vs issuing a visitor badge that opens one room and expires at 5pm.
Native Iceberg REST Catalog vs Apache Polaris
The Iceberg REST Catalog is a specification — an API contract that defines how engines talk to catalogs over HTTP. Polaris is one implementation of that spec. The distinction matters because the spec defines the protocol, not the server.
First — what is the Iceberg REST Catalog specification?
The Iceberg REST Catalog API (introduced in Iceberg 0.14, July 2022) is an OpenAPI specification that defines exactly which HTTP endpoints a catalog must expose and what they must return. It is the protocol — like TCP/IP is to networking or SQL is to databases.

The spec defines endpoints like: GET /v1/catalogs/{catalog}/namespaces → list namespaces GET /v1/catalogs/{catalog}/namespaces/{ns}/tables/{table} → load table + vended credentials POST /v1/catalogs/{catalog}/namespaces/{ns}/tables/{table}/snapshots → commit a new snapshot POST /v1/oauth/tokens → authenticate and get a JWT Any server that correctly implements these endpoints is a valid Iceberg REST catalog. Polaris is one. Gravitino is another. Nessie is working on it. You could even write your own in Flask in a weekend — and it would work with Spark, Trino, and Databricks as long as it returns the right JSON.
What Polaris adds on top of the bare REST spec
📄 Bare Iceberg REST Catalog
The specification — just the protocol
  • Engines (Spark, Trino) can discover and read/write tables by name
  • Tables are organised into namespaces/schemas
  • Atomic commits via CAS (compare-and-swap on metadata pointer)
  • Schema evolution, snapshot history, time travel all work
  • Authentication via OAuth2 bearer token
  • No concept of who can access which table — just authn, no authz model
  • No credential vending — you must configure storage credentials in the engine separately
  • No multi-tenancy — no concept of separate catalogs for separate teams
  • No governance — no policy enforcement, no audit trail
  • No catalog federation — only manages what it directly stores
  • No UI, no lineage, no classification
Think: a thin HTTP wrapper around a database table that stores metadata pointers. It speaks the spec but does nothing else.
🏔️ Apache Polaris
Implements the spec + adds a full platform
  • Implements the full Iceberg REST spec — same API, fully compatible
  • Credential vending — mints scoped STS tokens per table access (see Part 1)
  • RBAC model — Catalog Roles and Principal Roles controlling who can access which catalog/namespace/table
  • Multi-tenancy via Realms — hard isolation between business units, each with their own catalog hierarchy
  • Internal + external catalogs — Polaris can sync/proxy external catalogs (Nessie, Gravitino, Lakekeeper) and present them as first-class namespaces
  • OPA integration — externalize authorization decisions to Open Policy Agent for policy-as-code
  • Event logging — catalog-level audit of operations (who loaded which table, when)
  • Snowflake Open Catalog compatibility — zero-config integration with Snowflake's managed Polaris instance for cloud burst
  • PostgreSQL persistence — durable, queryable catalog metadata with HA support
  • Quarkus runtime — lightweight Java 21 server, fast startup, low memory, OCP-friendly
Think: a full catalog server that speaks the spec AND adds enterprise governance, security, and multi-tenancy on top.
The clearest analogy
REST spec is like HTTP
HTTP is a protocol specification — it defines how browsers and servers communicate. But "HTTP" alone isn't a web server. You need Apache, Nginx, or Caddy to actually run an HTTP server. They all speak HTTP (the spec), but each adds different things: caching, TLS termination, auth, rate limiting, logging.
Polaris is like Nginx
Polaris speaks the Iceberg REST spec (like Nginx speaks HTTP) AND adds access control, credential vending, multi-tenancy, and audit logging. A bare-bones REST catalog implementation is like a minimal Python Flask server — it speaks HTTP but has none of the production-grade features. Any engine that speaks the Iceberg REST spec works with both, but only Polaris gives you the enterprise platform.

The practical question — could you just write your own REST catalog?
Yes, technically. The Iceberg project ships CatalogHandlers — a Java class that implements the REST spec logic for you. You wrap it in a thin HTTP server, point it at a JDBC database for persistence, and you have a working Iceberg REST catalog. Netflix and Apple both run custom catalog implementations at massive scale.

But for RBC, the answer is no. A custom implementation means:
• You own every line of code that stores and retrieves table metadata
• You build credential vending from scratch or engines carry long-lived keys
• You build RBAC from scratch or have no table-level access control
• You have no enterprise support, no commercial backstop
• Your team needs deep Iceberg internals expertise to maintain it

Polaris gives you all of this, tested, maintained by 100+ contributors, with Snowflake and Dremio as commercial backstops. The build vs buy calculus is not close.
Summary: The Iceberg REST spec is the contract engines use to talk to any catalog. Polaris is an enterprise implementation of that contract — it speaks the same API, so any engine that works with the spec works with Polaris, but Polaris adds the credential vending, access control, multi-tenancy, and operational platform that a bare spec implementation doesn't include. Using "just the REST spec" without Polaris means you have to build or integrate everything else yourself.
