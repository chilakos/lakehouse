01
Does Privacera's SaaS control plane pass OSFI B-10 third-party risk review?
Risk & Compliance

Privacera's policy management control plane is SaaS-hosted in the US. Under OSFI Guideline B-10, all material technology arrangements with foreign service providers require documented assessment of jurisdictional risk, right-to-audit provisions, and exit/portability arrangements. This review must be completed before Privacera is used with production PII or PCI data.

"Does RBC's Third-Party Risk Management (TPRM) team assess Privacera's US-hosted control plane as acceptable under B-10, and on what timeline can that review be completed?"
If B-10 review passes
  • Proceed with Privacera as planned
  • Ensure contract includes audit rights, OSFI access, exit clause, subcontractor transparency
  • Data plane (engine agents) remains on-prem — only policy metadata crosses border
If B-10 review fails or is delayed
  • Fallback: OPA (Trino) + Kyuubi (Spark) — 100% on-prem, OSS
  • Adds operational complexity (two policy engines) but zero sovereignty risk
  • Databricks FGAC would need separate solution (Unity Catalog + engine-native)
  • Timeline impact: 4–6 weeks if fallback needed
Owner: CISO + TPRM + VP Enterprise Data
🔴 High — blocks Privacera production deployment

Is Write-Audit-Publish (WAP) branching a firm requirement for the Gold layer?
Strategic

Nessie's Git-for-data branching model enables Write-Audit-Publish workflows — writing to a branch, validating against compliance rules (Soda, Great Expectations), then atomically merging to the main production Gold layer. This directly addresses BCBS 239 data accuracy requirements and eliminates the risk of bad pipeline runs reaching consumers. However, it adds operational complexity and requires a second catalog service alongside Polaris.

"Does the data quality and risk management team require WAP-style atomic publish gates before data reaches the Gold layer? Is this a BCBS 239 must-have, or a nice-to-have we can address with Soda quality gates without branching?"
If WAP is required — add Nessie
  • Deploy Nessie alongside Polaris (write/validate on Nessie branch, merge to Polaris main)
  • Full multi-table atomic commits, regulatory snapshot tags, instant rollback
  • Nessie pre-1.0, Dremio-led — governance risk to acknowledge
  • Validate Privacera schema sync against Nessie REST before committing
If WAP is not required — Polaris alone
  • Use Soda / Great Expectations quality gates at pipeline level (not catalog level)
  • Iceberg snapshot isolation provides point-in-time reads without branching
  • Simpler stack — one catalog service, one policy to maintain
  • BCBS 239 data accuracy addressed via lineage + quality gates, not WAP
Owner: VP Enterprise Data + Risk Data Management + BCBS 239 owner
🟡 Medium — can be a Phase 2 decision

What is the exit strategy if Polaris fails to graduate from ASF Incubation?
Risk & Compliance

Apache incubating projects have a small but non-zero probability of failing to graduate — due to governance failures, community fragmentation, or commercial capture. If Polaris is abandoned, we need a catalog migration path that doesn't require moving data files (Iceberg tables are self-describing — only the catalog pointer changes). The risk is not catastrophic but requires a documented contingency.

"What is architecture's view on the Polaris abandonment risk, and is a documented fallback catalog (Gravitino or custom HMS) sufficient for the risk management team to approve production deployment?"
Mitigating factors
  • Iceberg REST spec is catalog-agnostic — switching catalogs is a config change, not data migration
  • Snowflake and Dremio both have commercial managed versions — commercial continuity exists
  • Gravitino (ASF TLP) is a viable fallback — can federate Polaris today, replace it tomorrow
  • AWS Glue and HMS are always available as regression fallbacks
Residual risk
  • Catalog migration would take 2–4 weeks of platform engineering effort
  • No data loss — Iceberg data files are unaffected by catalog changes
  • Privacera schema sync would need to be re-pointed to new catalog REST API
  • Net risk assessment: low impact, low probability — manageable
Owner: Chief Architect + Enterprise Risk
🟡 Medium — document and accept, or require formal risk approval

How do we enforce Import mode as a governance constraint in Fabric?
Governance

ADR-010 establishes that Fabric Import mode (not DirectLake) is mandatory for any table containing PII or PCI data — because DirectLake bypasses T-SQL Dynamic Data Masking entirely. This decision must be operationalized: enforced at the workspace provisioning level, communicated to Fabric developers and data consumers, and audited to prevent accidental DirectLake use on sensitive datasets. Without enforcement, this architectural decision becomes a policy recommendation that can be silently violated.

"Who owns enforcement of the Import mode mandate in Fabric, and what controls prevent a developer from accidentally enabling DirectLake on a PII-tagged Lakehouse item?"
Technical enforcement options
  • Fabric workspace governance policy — restrict DirectLake on tagged items
  • Purview sensitivity labels trigger DLP alert on DirectLake activation for PCI/PII items
  • CI/CD pipeline check — validate Import mode in semantic model deployment
  • Quarterly Fabric workspace audit — detect DirectLake on classified tables
If not enforced
  • A developer enables DirectLake on a PII table → DDM bypassed → PCI data exposed in Power BI reports without masking
  • OSFI B-13 / PCI-DSS control failure — potential regulatory finding
  • JoAnn's DA team and Saurabh's PM team need to be trained on this constraint
Owner: VP Enterprise Data + JoAnn (DA Lead) + Fabric workspace admin
🔴 High — must be in place before any PII data lands in Fabric

Who owns the Privacera schema sync and policy authoring process at scale?
Technical

Privacera syncs table/column schema from Polaris to build its policy model. For tens of thousands of tables, automated PII/PCI discovery (Privacera classifiers + Atlas) must classify columns, and someone must own the Privacera policy authoring process. Without a clear owner and governance process, policies will either be too permissive (security risk) or require manual intervention for every new table (operational bottleneck).

"Who owns the Privacera policy lifecycle — initial classification, policy authoring, change management, and periodic access reviews? Is this Gautam's Lakehouse team, Irene's QA function, the CISO team, or a new data governance role?"
Recommended operating model
  • Automated baseline: Privacera classifiers auto-classify new tables on schema sync; default-deny for PII/PCI columns until policy is approved
  • Data owner approval: Table owner approves access policy before any analyst group can access the table
  • Quarterly access review: Nabi (Data Modeller) / JoAnn's team review role-to-table assignments
  • CISO oversight: PCI-classified tables require CISO sign-off before any new role grants
Without clear ownership
  • New tables default to open access — PII exposed to unauthorized roles
  • Policy drift — stale role assignments accumulate over time
  • PCI DSS Requirement 7 violation — access not reviewed periodically
  • Bottleneck — data consumers blocked waiting for policy approvals
Owner: VP Enterprise Data + Gautam + Nabi + CISO
🔴 High — must be defined before Privacera goes to production
