The goal: one authoritative definition of every business metric — NII, VaR, LCR, customer count — consumed identically by Power BI dashboards, RBC Assist AI queries, Tableau analysts, and ML pipelines. Three architecture patterns evaluated against RBC’s confirmed stack.

Both Power BI and RBC Assist read the same DAX measure. If someone changes the definition of [Net Interest Income] in the Fabric model, it updates everywhere simultaneously — report visuals and AI answers in the same refresh cycle. This is "define once" working today.
Where "define once" breaks down: Fabric’s DAX measures are not queryable by Tableau, ML pipelines, or AI agents that need raw data or complex SQL. Those consumers fall back to Trino directly — which means they bypass the Fabric semantic model and the metric definition is lost. They either rewrite the metric in SQL themselves, or get a different number.

Why Fabric’s DAX can’t serve everything
DAX limitations for agent/ML use cases
  • No REST/GraphQL API — XMLA only. Python agents can’t call DAX cleanly
  • No real-time Iceberg — always reads the Delta copy (minutes-to-hours lag)
  • DAX cannot express: window functions, rolling aggregations, multi-join feature extraction, 50k-row ML datasets
  • No row-level data export for model training — Fabric returns summaries, not raw rows
  • Fabric Data Agent handles simple NL → KPI queries. Multi-hop reasoning ("customers with 3+ products AND declining engagement") requires complex SQL
Tableau limitations through Fabric
  • Tableau cannot connect to the Fabric Import semantic model directly — no XMLA reader in Tableau that exposes DAX measures as governed objects
  • Tableau can connect to the Fabric SQL Analytics Endpoint via ODBC — but this exposes raw Delta tables, not the DAX measures
  • Result: Tableau analysts rewrite metric logic in SQL themselves → drift from the Fabric definition
  • BCBS 239 audit risk: "NII" in Tableau ≠ "NII" in Power BI if both sides define it independently
AtScale Pattern 3 places AtScale between Gold Iceberg and all consumers. Fabric imports from AtScale (pre-aggregated, governed) instead of raw Gold. Tableau and agents also connect to AtScale. One metric definition, served to every surface. This is "define once" extended to the full consumer estate.

What changes vs today
Gains
  • True single metric registry — change NII definition once in AtScale, it propagates to Fabric, Tableau, agents simultaneously
  • BCBS 239 compliance — every number in every tool traces back to the same definition. Audit question "how is NII calculated?" has one answer
  • Fabric Import is faster — Fabric imports pre-aggregated AtScale output instead of joining raw FSDM tables. Smaller dataset, faster refresh, lower F-SKU memory pressure
  • AI agents get business context — AtScale REST + MCP server gives agents governed metric definitions, not raw schema
  • Excel coverage — MDX cube exposure for risk/treasury teams who work in Excel pivot tables
Costs & risks
  • AtScale in Fabric refresh chain — if AtScale has an outage, Fabric can’t refresh. New single point of failure for 1,000 Power BI reports. Requires enterprise SLA before production.
  • Two authoring environments remain — metrics defined in AtScale, then DAX measures in Fabric reference them. Still need both. The drift problem is reduced but not eliminated.
  • New vendor, new B-10 review — AtScale must pass OSFI third-party risk assessment before it sits upstream of Fabric.
  • Implementation complexity — AtScale’s Hadoop origins. POC against Trino/Polaris/MinIO required before commitment.
  • Procurement cycle — enterprise licensing, unpublished pricing. 3–4 months from decision to production.
Critical dependency: Fabric’s NL-to-DAX / RBC Assist path remains independent of AtScale. The Fabric Data Agent still reads Fabric’s own DAX measures — not AtScale directly. So even in Pattern 3, there are technically two metric layers: AtScale (upstream definition) and Fabric DAX (downstream projection for Power BI + AI). The goal is to keep them in sync through governance process, not through perfect technical unification.
The architectural goal — and where each option lands
What "define once, serve AI and BI" actually requires
  1. One authoritative metric definition — "NII" is calculated one way, everywhere
  2. Consumed by Power BI — fast, in-memory, certified, with RLS
  3. Consumed by RBC Assist (AI) — NL query returns the same NII as the Power BI report
  4. Consumed by Tableau — analyst connects and gets the governed metric, not raw SQL
  5. Consumed by agents / ML — programmatic access to the same business context, not raw schema
1Fabric alone (today)
Solves requirements 1–3. Fails 4 and 5. Tableau gets raw Trino. Agents get raw schema.
  • Already built and confirmed
  • No new vendor
  • RBC Assist + Power BI: genuinely unified
  • Tableau metric drift — BCBS 239 risk
  • Agents have no business context
2AtScale Pattern 3 (full vision)
Solves all 5 requirements. AtScale is the single definition layer. Fabric, Tableau, agents all consume from it.
  • True single metric registry
  • BCBS 239 — one definition everywhere
  • Agents get business context via MCP
  • Fabric refresh faster (pre-aggregated)
  • AtScale in Fabric refresh chain = new SPOF
  • OSFI B-10 review required
  • POC on Trino/Polaris stack first
  • Requires Q-10 Tableau scope confirmed
3Starburst (partial)
Solves 1–2 partially through data products. Fabric still imports raw Gold (no upstream semantic). Tableau gets governed SQL views. Agents get data products API.
  • Trino upgrade path — less new technology
  • Data products serve agents well
  • Lighter semantic layer than AtScale
  • Fabric still importing raw Gold
  • No MDX for Excel
4dbt MetricFlow
Solves metric consistency in theory but conflicts with ADR-005 (no dbt). YAML definitions in source control, but requires dbt Cloud SaaS. Not recommended.
  • Direct ADR-005 conflict
  • dbt Cloud SaaS — OSFI B-10 exposure
  • Dual stack with Python transforms
Sequencing recommendation:
Now: Operate with Fabric alone. Power BI + RBC Assist are unified today. Accept that Tableau has no governed metrics for the moment.
Q-10 answered (JoAnn + Saurabh): If Tableau = certified reporting → run AtScale POC against Trino/Polaris/MinIO. If POC passes and OSFI B-10 review clears → implement Pattern 3. This is the path to the full "define once" vision.
Don’t skip the POC. AtScale’s Hadoop origins have caused friction on modern Trino/Iceberg stacks. Validate before committing it as a dependency in the Fabric refresh chain.
